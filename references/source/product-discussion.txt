## 一、先确定项目定位和本届能交付什么

### 1. 建议聚焦的场景

**洪涝导致道路受阻的县域或城市周边地区，应急指挥人员需要用有限的无人机、电池和通信资源，向多个受灾点投送物资。**

选择这个场景有利于把你们已有的数模研究、智慧城市主题和实际产品需求连起来。第一阶段主要面向三个角色：

| 使用者 | 主要工作 | 系统应帮助其完成什么 |
|---|---|---|
| 应急指挥人员 | 确定保障重点、分配有限资源 | 判断哪些需求能按时完成，比较不同方案，处理资源不足 |

第一阶段围绕**应急物资投送与运输通信保障**展开。人员识别、伤情判断、载人转运和低层飞行控制分别需要另一套数据、模型与验证过程，可以在产品路线中说明，但不宜同时作为首版交付目标。

## 二、你们现有数模成果，适合怎样转化

你们原题已经具备比较完整的资源约束基础：**1 个基地、15 个服务区、80 个不可拆箱件、3 型共 8 架运输无人机、14 组电池，以及 2 架中继无人机和 6 组中继能源组件**，同时涉及地形、时间窗、运输与通信协同。这个基础能够支持比普通航线规划更深入的产品。山区洪涝灾害下无人机运输与通信协同优化(6).docx

建议这样继承：

| 已有研究能力 | 在产品中的用途 | 本次需要增加的能力 |
|---|---|---|
| 单点物资组批、装载与架次优化 | 快速生成基础运输任务 | 接受用户实际库存和需求，处理新增与取消 |
| 异构无人机与电池联合排程 | 生成机体、电池和架次甘特图 | 实际位置、当前电量、充电状态、设备退出 |
| 运输与中继通信协同 | 显示通信依赖和中继服务安排 | 通信余量、服务失效事件、动态联动修复 |
| 几何与链路的连续检查 | 构成独立方案检查器 | 定位具体冲突对象、时间和位置 |
| 固定任务下的资源分区分析 | 分析资源瓶颈和增配需求 | 用户修改资源后重新计算边际收益 |

这里有三个特别值得转化为创新动机的发现。

**第一，现有求解过程需要改造，才能支持交互。**论文中 Q2 扩充候选与联合搜索约用了 10 小时；Q3 最后一轮的时间阶段、能耗阶段分别记录了约 404 秒和 721 秒。因此，系统应采用“快速初解—限时改进—事件局部修复”的路线。

**第二，现有最优附近方案的余量较薄。**论文报告的最低返航 SOC 约为 20.096%，只比题设的 20% 下限高 0.096 个百分点。这为考虑风况、电池衰减和模型误差提供了直接动机。

**第三，通信也需要考虑模型偏差。**论文的固定通信来源压力测试中，提高 0.5 dB 要求后出现累计不满足时长；该指标是逐机累计时长，不能解释成整个系统同时断网的时间。产品应能说明通信假设、余量和受影响任务。以上都属于论文报告结果，本次尚未对原工程独立复跑。D26106140150(1).pdf

所以，这次最有价值的升级是：

> **把确定场景下的优化能力，扩展为支持实际输入、执行状态、突发事件和可解释取舍的调度系统。**

## 三、系统完整的输入—计算—执行—反馈流程

建议围绕下面这条业务流程设计：

1. 创建救援场景，选择地图和场景时间。
2. 导入需求、库存、无人机、电池和保障资源。
3. 在地图上补充临时限制区、投送点状态和风险信息。
4. 设置必须保障的需求、截止时间和调度偏好。
5. 计算候选方案，并查看资源与任务安排。
6. 比较方案、确认采用、导出任务单。
7. 接收设备退出、新需求或地图变化事件。
8. 修复未来计划，展示变化并保留完整记录。

### 1. 输入不能停留在“无人机数量”

无人机数量只是资源的一部分。真正决定方案能否执行的，是资源实体及其当前状态。

| 输入类别 | 关键内容 | 设计重点 |
|---|---|---|
| 场景 | 起始时间、区域、基地、坐标参考、地图版本 | 所有计算绑定同一份场景快照 |
| 地图与地形 | DEM、已配准影像、障碍物、限制区、落点 | 记录来源、时间、覆盖范围与缺失区域 |
| 救援需求 | 位置、物资种类、数量、紧急等级、截止时间 | 区分必须保障、可延期和普通补给 |
| 实际物资 | 箱件 ID、重量、体积、类别、所在仓库 | 不可拆箱作为独立对象管理 |
| 无人机机型 | 载重、容积、速度、能耗参数、支持的任务 | 机型是规格模板 |
| 无人机实体 | 机体 ID、当前地点、状态、可用时间 | 每架机体独立占用和排程 |
| 电池实体 | 电池 ID、兼容型号、容量、SOC、SOH、位置 | 每块电池都能追踪，不能被重复使用 |
| 基地保障 | 充电端口、总功率、起降位、装卸能力 | 完整版加入地面保障容量限制 |
| 通信资源 | 网关、中继位置候选、覆盖条件、服务窗口 | 同时检查运输机到中继、中继到网关 |
| 动态事件 | 设备退出、新需求、交付延迟、落点不可用 | 带稳定事件 ID、发生时间和接收时间 |
| 调度策略 | 保障要求、时间偏好、费用参数、额外余量 | 保留明确且可解释的参数含义 |

建议首版用 **CSV、GeoJSON 和表单编辑**打通流程，随后增加 Excel 导入和字段映射。界面提供可下载模板、示例数据、逐行错误提示，避免让用户猜列名和单位。

有两个状态设计尤其重要：

- **需求与库存分开。**受灾点“需要 20 箱饮水”，不等于仓库已经有 20 个可分配箱件。
- **计划与执行事实分开。**物资已经装机后，即使取消计划，也不能自动恢复成仓库可用库存。

物资状态可以设计为：

**可用 → 已预留 → 已装载 → 在途 → 已交付**，异常回收和重新入库另外记录。

### 2. 输出需要具体到任务和资源

用户点击一个方案后，应能得到：

| 输出 | 用户实际用途 |
|---|---|
| 方案摘要 | 了解保障范围、预计完成时间、费用或代理成本、主要瓶颈 |
| 逐箱任务表 | 查每个箱件由哪架机、哪一架次运到哪里 |
| 架次任务单 | 查装载、准备、起飞、投送、返航、电池和通信安排 |
| 地图航路 | 查经过哪些位置、地形高度、限制区和通信依赖 |
| 资源甘特图 | 查机体、电池、中继与充电资源的占用关系 |
| 未满足需求清单 | 查哪些任务没完成，以及具体原因 |
| 重规划差异 | 查哪些任务改派、延后或保持不变 |
| 复盘与导出 | 下载任务表、方案数据、事件记录和结果摘要 |

**“无完整方案”本身也应是一种有用输出。**

例如，系统可以说明：

> 当前搜索预算内未找到全部按时完成的方案。某需求点受载重与截止时间共同限制；增加兼容电池后，候选方案的保障范围有所扩大。

这里需要区分“求解器证明模型无解”和“在给定时间内还没找到可行解”。OR-Tools 的 `INFEASIBLE`、`UNKNOWN`、`FEASIBLE`、`OPTIMAL` 有不同含义，界面应保留这些区别。[developers.google.com](https://developers.google.com/optimization/cp/cp_solver?utm_source=chatgpt.com)

## 四、“实时地图采集生成”应分三个层级实现

这个功能有价值，但必须把地图业务更新、数据处理和航测建图的工作量区分清楚。

### 第一层：现场业务信息实时更新

最适合首版：

- 新增受灾点或需求点。
- 修改投送点是否可用。
- 录入临时限制区。
- 标注危险区域。
- 更新无人机、仓库或电池状态。

这些信息来自人工录入、表格上传或后续遥测接入。更新后生成新的状态版本，触发影响分析和必要的重规划。

### 第二层：导入已经配准的地图和地形数据

支持 GeoTIFF、DEM、GeoJSON 等资料，进行：

- 坐标参考检查与必要转换。
- 地形覆盖范围检查。
- NoData 区域识别。
- 数据版本登记。
- 地图预览与航段计算。

坐标处理要保存原始参考系统，并选择适合当前区域的米制投影。高程还涉及垂直参考，未知基准不应由软件猜测。GDAL 提供重投影及有条件的垂直转换能力，但依赖输入具备足够的参考信息。[GDAL documentation](https://gdal.org/en/stable/programs/gdalwarp.html?utm_source=chatgpt.com)

### 第三层：从无人机照片生成地图

放在后续版本：

1. 上传带必要拍摄信息的影像。
2. 执行摄影测量处理。
3. 生成正射影像、点云和地表模型等结果。
4. 对结果进行检查、配准和质量确认。
5. 人工确认后生成新的可用地图版本。

OpenDroneMap 可以输出正射影像以及 DSM、DTM 等成果，适合作为这一阶段的处理工具。这个过程需要按照片规模和硬件单独评估耗时。[OpenDroneMap 3.6.0 documentation](https://docs.opendronemap.org/outputs/?utm_source=chatgpt.com)

同时要区分三类含义：

- **洪水范围**反映地表状态；
- **落点不可用**影响投送任务；
- **空域限制**影响飞行路线。

它们可能相关，但不能自动互相等同。你们原题的 30 米 DEM 也不能覆盖所有建筑、树木和线缆细节，因此地图质量应成为方案说明的一部分。

## 五、算法总体路线：把空间、装载、排程和验证连接起来

建议采用分层求解，先保证闭环可用，再增加学习模块。

```mermaid
flowchart TD
    A["现场输入与动态事件"] --> B["数据校验与状态快照"]
    B --> C["候选航路与装载方案"]
    C --> D["机体、电池、中继联合排程"]
    D --> E{"独立约束检查"}
    E -->|通过| F["方案比较与确认"]
    E -->|发现冲突| D
    F --> G["执行记录与资源更新"]
    G --> B
```

### 1. 空间层：生成多条候选航路

首版可以从你们已有地形模型起步，逐步加入：

- A* 或可见图生成候选绕行路径。
- 地形高度与飞行高度检查。
- 限制区、危险区和落点状态。
- 路径长度、预计能耗、通信依赖等属性。

每对关键点保留少量有差异的可行候选，例如距离较短、余量较大、通信条件较好的路线。

### 2. 装载层：把箱件组合成可运输批次

考虑：

- 重量与体积双约束。
- 不可拆箱。
- 物资类别和机型适配。
- 投送点顺序。
- 时间窗。
- 装卸和准备时间。

可以复用你们的枚举、动态规划或候选路线生成模块，为排程层提供可选运输任务。

### 3. 排程层：分配实际资源

排程对象包括：

- 具体哪架无人机执行。
- 使用哪块电池。
- 起飞、投送、返航时间。
- 电池何时充电、何时再次可用。
- 中继在哪个时间窗提供服务。
- 完整版中的充电端口、地面人员和起降位。

可采用 **候选方案 + CP-SAT**，结合启发式初解与局部搜索。已有可行解尽早返回，剩余预算继续改进。

### 4. 验证层：独立重算关键约束

独立检查器至少验证：

- 箱件没有重复运输或凭空出现。
- 载重、体积和机型适配正确。
- 机体、电池和中继没有重叠占用。
- 物资所在位置与装载过程一致。
- 电量和储备满足要求。
- 截止时间和路线限制满足要求。
- 通信依赖在所用模型下成立。

求解器使用整数化时间或简化候选时，检查器应使用原始物理量重新计算关键结果。这样既能发现实现问题，也能向用户说明具体冲突。

## 六、时间优先、成本优先和均衡优先，怎样做才有意义

建议采用分层决策：

### 第一层：硬约束

载重、库存、电池、资源互斥、路径限制、必须满足的通信条件等属于共同可行域。切换偏好不能放松这些条件。

### 第二层：救援保障要求

确定必须完成的需求、硬截止和不可牺牲的基本保障要求。

若资源不足，应进入单独的部分保障建议流程，让用户看到缺口和影响。不能让“成本优先”通过少送一批关键物资，得到看似更便宜的完整方案。

### 第三层：在共同保障范围内比较偏好

| 策略 | 优化重点 | 界面应说明的取舍 |
|---|---|---|
| 时间优先 | 关键交付时间、整体完成时间 | 可能增加架次、能源或资源占用 |
| 费用优先 | 能源、架次、设备占用、人工等成本 | 可能使部分非紧急任务更晚完成 |
| 均衡优先 | 时间、费用、基本保障等待时间 | 说明各维度改善与损失 |
| 额外余量优先 | 保留更多电量或通信余量 | 可能增加绕行、换电或中继资源 |

费用模型可以写成：

\[
C=C_{\text{能源}}+C_{\text{架次}}+C_{\text{设备占用}}+C_{\text{人工}}+C_{\text{增配}}
\]

实际价格未知时，使用明确说明的代理成本，或让用户配置价格。不要直接把能耗换成未经验证的人民币收益。

“均衡保障”也要定义清楚。建议关注**每个服务点达到最低基本保障组合的时间**，例如达到某个饮水、食品和急需物资组合，而不是只统计送到一个点多少箱。这样能够降低物资重量和箱数差异带来的偏差。

比较卡片必须使用相同的指标口径，尤其要区分：

- 最后一个需求完成投送的时间；
- 最后一架无人机返航的时间；
- 所有无人机累计作业时间。

## 七、建议重点做的三个创新方向

### 创新一：基于资源依赖关系的动态局部修复

**这是最适合作为项目主创新的方向。**

#### 具体问题

一块电池退出，影响可能沿着后续共享关系传播；一个中继窗口失效，可能同时影响多架运输无人机。

因此，事件影响分析不能只看“故障设备当前关联的那一个任务”。

#### 方法设计

构建由任务、机体、电池、中继窗口和航段组成的资源依赖关系：

1. 事件首先命中直接受影响对象。
2. 沿未来预约和先后关系扩展影响范围。
3. 保留已经完成的事实。
4. 对在途、已装载和已承诺任务设置相应约束。
5. 对受影响的未来部分进行修复。
6. 独立检查后给出新方案和变化清单。

优化时增加计划变更代价，例如：

- 改派次数。
- 起飞时刻变化总量。
- 箱件重新装载次数。
- 中继位置和服务窗口变化。

如果原计划已不满足安全或物理约束，冻结和变更代价不能阻止必要调整。

#### 用户能看到的价值

用户不仅得到新方案，还能看到：

> 哪些任务受到了影响；哪些任务保持不变；为什么某个后续架次也要调整；本次重规划改变了多少已协调安排。

#### 实验重点

在相同计算预算下，对比局部修复和全量重算，观察：

- 首个可行方案响应时间。
- 保障水平。
- 修改任务数量。
- 原有承诺的保留程度。

这是一个能够同时体现算法贡献、工程深度和使用价值的切入点。

### 创新二：运输、电池与通信的稳健协同

你们已经有运输与通信协同基础，下一步可以加入实际执行中的不确定性。

#### 建议先考虑的因素

- 电池 SOH 和当前 SOC。
- 载荷变化。
- 风况或能耗参数偏差。
- 投送服务时间变化。
- 通信链路参数偏差。
- 中继或电池不可用事件。

第一阶段可以先做**情景模拟和参数敏感性实验**。有真实飞行日志后，再研究能耗残差预测或分位数预测。

#### 建模原则

硬约束仍然必须满足。稳健优化可以用于控制迟到、保障不足等服务损失的尾部风险；额外储备可以作为可配置的运营策略。

你们题设中的 20% 下限属于基准配置。实际系统应记录它的来源，并根据机型、作业条件和验证结果确定适用配置。

#### 通信不能只画覆盖圆

对于单中继两跳链路，要同时检查：

- 运输无人机到中继的接入链路；
- 中继到网关的回传链路；
- 相应时间段的中继可用性与能源状态。

你们已有的连续区间检查可以继续发挥作用。后续再增加容量、切换开销和多任务竞争。

这一方向能够展示“在模型参数改变或资源失效时，方案如何保持保障能力”，但模拟实验的结论需要明确限定在所用模型与场景内。

### 创新三：学习辅助搜索，把 AI 用在求解决策上

**优先建议做轻量模型辅助邻域选择。**

动态调度中，可用的修复动作有很多，例如：

- 移除并重新插入一组任务。
- 交换不同无人机的任务。
- 调整批次装载。
- 更换电池分配。
- 调整中继窗口。
- 局部改变访问顺序。

AI 模块根据当前状态，预测哪些动作更值得尝试。

#### 输入特征

可以包括：

- 剩余任务数与紧急任务比例。
- 时间窗紧张程度。
- 可用无人机、电池数量。
- 当前资源冲突类型。
- 任务延迟和电量余量。
- 不同算子近期的改进效果。

#### 训练与执行方式

1. 用非学习版本积累搜索日志。
2. 记录算子带来的目标改善、耗时和可行性。
3. 训练随机森林、树模型或简单排序模型。
4. 在线选择更有希望的修复动作。
5. 任何候选结果仍需经过约束检查。

LENS 的研究使用学习方法辅助车辆路径问题中的邻域选择，并提供作者代码，适合作为这条路线的参考；它的约束需要按你们的电池、通信和执行状态重新设计。[arxiv.org](https://arxiv.org/abs/2403.08839?utm_source=chatgpt.com)

训练与测试必须按完整场景或事件序列划分，避免把同一地图和任务实例的相似日志同时放进训练与测试。

### 相关论文如何借鉴

| 参考工作 | 借鉴点 | 在本项目中的位置 |
|---|---|---|
| LENS，2024 预印本 | 学习辅助邻域选择 | 优先尝试的 AI 模块 |
| PIP，NeurIPS 2024 | 提前识别会导致后续不可行的动作 | 后续约束处理研究 |
| CaR，ICLR 2026 | 构造与修复过程的协同 | 后续求解框架研究 |
| IET 2026 应急物流研究 | 通信不确定性下的动态路由与学习启发式结合 | 必须认真比较的近邻工作 |

PIP 和 CaR 已在相应会议正式论文页面公开，适合研究复杂约束处理，但不宜成为当前短期原型的前置依赖。[proceedings.neurips.cc](https://proceedings.neurips.cc/paper_files/paper/2024/hash/a9d2a5fd12d34250c21b5e4fa8d906b0-Abstract-Conference.html?utm_source=chatgpt.com)

还要注意，2026 年已有研究把通信不确定性、强化学习、启发式搜索和动态应急物流联系起来。因此，创新表述需要落到你们解决的具体问题，例如**有限电池和中继共享引起的依赖传播、执行承诺下的局部修复，以及相同响应预算下的保障与稳定性改善**。这些应作为拟验证贡献，经过实验后再确定最终表述。[Wiley Online Library](https://ietresearch.onlinelibrary.wiley.com/doi/10.1049/itr2.70302?utm_source=chatgpt.com)

## 八、增加一个很实用的能力：资源增配分析

当任务无法全部完成时，用户通常还会问：

> 多一块电池有没有用？增加一架无人机，还是增加一个充电端口更有效？

系统可以提供资源情景比较：

| 用户操作 | 系统计算 | 返回内容 |
|---|---|---|
| 增加一块兼容电池 | 重新排程 | 新增可保障任务、时间变化、资源利用变化 |
| 增加一架某型无人机 | 比较候选机型 | 哪种机型对当前瓶颈更有效 |
| 增加一个充电端口 | 重算充电排程 | 是否缓解排队、是否只是转移瓶颈 |
| 放宽某个非关键截止时间 | 重新计算 | 减少哪些资源需求、影响哪些服务 |
| 提高额外储备 | 重算能量约束 | 哪些任务需要换机、绕行或增加架次 |

这个功能能服务救援演练、设备配置和采购讨论。

实现时必须真实重新求解。没有最小性证明时，输出“当前计算预算下找到的增配建议”，而不是断言这是全局最少资源。

## 九、前端建议：三个主页面构成完整工作流

文档中已经加入工作台布局示意图。它是界面设计稿，其中计算指标使用占位说明，方便你们讨论视觉和交互。

### 页面一：场景与资源

目标是让用户顺利把现实信息输入系统。

建议结构：

- 顶部显示场景名称、时间、数据版本和整体就绪状态。
- 左侧为导入步骤：地图、需求、物资、机队、电池、策略。
- 中间为资源表格与字段编辑。
- 右侧为地图预览或当前对象详情。
- 底部显示错误和缺失项。

关键交互：

- 点击表格行，在地图定位。
- 点击地图点，打开对应需求。
- 上传后先预览，再确认导入。
- 错误具体到行号和字段。
- 无法调度的需求保留在清单中，并说明原因。
- 每份地图和业务数据都能看到来源与更新时间。

### 页面二：调度工作台

建议布局为：

- **左侧约 20%：任务与机队列表。**
- **中间约 55%：主要地图。**
- **右侧约 25%：候选方案与详情。**
- **底部：与地图联动的资源时间轴。**

顶部指标控制在 5—6 个：

- 必须保障任务按时完成情况。
- 未满足需求数量。
- 预计完成时间。
- 能耗或费用。
- 最低电量余量。
- 当前方案状态。

中间地图支持：

- 需求点按紧急程度和完成状态显示。
- 路线选择、高亮与阶段区分。
- 限制区、地形和通信图层开关。
- 点击架次查看所运箱件、电池和中继依赖。
- 播放某个时刻的计划状态。

右侧放时间优先、费用优先、均衡优先卡片。选择后，下方显示具体取舍，例如“完成时间变化、架次变化、费用变化、基本保障等待变化”。

底部甘特图至少有两个视角：

1. 无人机视角：准备、飞行、投送、返航和等待。
2. 电池视角：使用、充电、等待和再次使用。

### 页面三：事件复盘与资源分析

建议包含：

- 事件时间线。
- 原方案与新方案对比地图。
- 改派、延期和保留任务清单。
- 重规划耗时和保障变化。
- 资源增配情景。
- 方案与日志导出。

一个很适合比赛演示的操作是：

> 将一架尚未起飞的无人机设为不可用，观察受影响任务、修复过程、改派范围和未满足需求。

这样能在较小实现范围内，展示完整动态闭环。

### 视觉风格

建议默认采用：

- 浅色背景，深蓝导航与标题。
- 青绿色表示正常与已验证状态。
- 橙色表示待处理事件。
- 红色用于明确冲突或紧急异常。
- 表格、地图、时间轴使用统一选择状态。
- 颜色同时配合文字和图标表达含义。

美观的重点是信息层级、留白、字体和联动一致性。让使用者能迅速找到“当前在哪个场景、采用哪个方案、还有哪些任务没完成”。

## 十、工程架构：先把一套完整流程做扎实

建议首版采用较简单的架构：

| 层次 | 建议技术 | 主要职责 |
|---|---|---|
| 前端 | React、Vite、TypeScript | 页面、表格、方案比较、事件操作 |
| 地图 | MapLibre GL JS | 路线、点位、图层和地形展示 |
| 后端 | FastAPI、Pydantic | 数据校验、接口、计算任务、结果管理 |
| 算法 | Python、OR-Tools、启发式搜索 | 路径候选、装载、排程和修复 |
| 地理处理 | GDAL、Rasterio、Shapely | 栅格、坐标、几何与空间检查 |
| 存储 | SQLite 与文件目录 | 场景、状态、方案、事件和地图文件 |
| 后台计算 | 独立工作进程 | 限时求解、取消、进度与日志 |

MapLibre 的官方示例提供了地形渲染方式，适合用于地图工作台；地形数据的准备与正确性仍由数据处理流程负责。[MapLibre GL JS](https://maplibre.org/maplibre-gl-js/docs/examples/3d-terrain/?utm_source=chatgpt.com)

### 最值得认真做的四个工程点

**1. 场景版本与计算快照。**  
每次计算固定输入快照。用户修改资源后，旧计算结果不能覆盖新状态。

**2. 确认方案与资源预约保持一致。**  
版本比较、当前计划切换和资源预约应在同一数据库事务中完成，发生冲突时整体回滚。

**3. 事件幂等。**  
同一事件重试使用相同 `event_id`，后端唯一约束去重，避免重复扣库存或重复取消任务。

**4. 失败状态可解释。**  
输入错误、模型无解、超时未找到解、已有可行解但尚未证明最优，应在接口和界面上分别表示。

后台计算接口宜先返回 `job_id`，前端轮询状态并展示已验证候选。对于复杂求解，OR-Tools 支持设置时间限制等控制项，适合做有限预算的交互计算。[developers.google.com](https://developers.google.com/optimization/cp/cp_tasks?utm_source=chatgpt.com)

### 算力建议

**按这条技术路线，核心系统和首版演示不需要 4090。**

主要负载是组合优化、地理计算和状态管理，优先考虑 CPU 性能、内存和数据规模。可以先在现有设备上运行，小规模开发以 16 GB 内存尝试，较大候选池或地形数据优先准备 32 GB；这是开发配置建议，最终用实测决定。

训练轻量树模型也不需要把高端显卡作为前置条件。后续如果引入大量影像处理或视觉模型，再单独评估硬件。

### 真机接入路线

完整版可以从 PX4 软件在环仿真和 MAVSDK 任务接口开始做适配。PX4 官方支持仿真工作流，MAVSDK 提供任务上传、执行和跟踪能力；实际机型支持范围和任务约束要逐项验证。[PX4 Guide (main)](https://docs.px4.io/main/en/simulation/?utm_source=chatgpt.com)

首版输出可以先落到调度建议和任务单，算法闭环、飞控仿真和真实飞行分别留存验证证据。

## 十一、怎样证明项目的创新和实用性

### 1. 基础功能验收

首版至少应通过这些场景：

- 换一组需求和资源，产生新的计算结果。
- 减少库存后，系统保留未满足需求并指出缺口。
- 修改无人机或电池可用状态，资源安排随之变化。
- 比较两种偏好时，关键保障范围和指标口径一致。
- 注入设备退出事件，旧计划受影响部分被识别并修复。
- 重复发送同一事件，不重复影响业务状态。
- 确认过期方案时，被版本检查拒绝。
- 现场演示能使用预先准备的本地数据与资源。

### 2. 算法对照实验

建议保留以下基线：

| 方法 | 用途 |
|---|---|
| 最早截止优先的可行贪心 | 衡量基础启发式水平 |
| 原数模静态方案 | 核对已有模型和静态性能 |
| 周期全量重算 | 比较动态重规划方式 |
| 事件触发的非学习局部搜索 | 判断学习模块是否真的有贡献 |
| 完整方法 | 评估整体效果 |
| 去掉某个模块的消融方法 | 判断依赖图、稳定性代价、学习选择等各自作用 |

所有对比统一：

- 输入数据与物理模型。
- 任务可见时间。
- 计算预算和线程数。
- 资源与截止条件。
- 成本和交付指标口径。

知道全部未来事件的离线方法，可以作为信息更充分的参考，但不能与普通在线方法混为一类。

### 3. 建议指标

| 维度 | 重点指标 |
|---|---|
| 救援效果 | 关键需求按时保障、未满足数量、最低基本保障完成时间 |
| 调度效率 | 最后投送时间、最后返航时间、架次、累计占用 |
| 成本能源 | 能耗、配置价格下的费用、额外资源使用 |
| 响应能力 | 首个已验证可行解耗时、重规划耗时、较慢场景表现 |
| 方案稳定性 | 改派次数、起飞时刻变化、重新装载次数 |
| 约束可靠性 | 资源冲突、电量不足、通信不满足等检查结果 |
| 使用效果 | 用户完成导入、方案选择和事件处理所需时间与错误数 |

对于你们原题规模，可以暂把：

- **30—60 秒获得首个可行方案；**
- **5—10 秒完成受限范围内的局部修复；**

作为开发优化目标。它们需要首轮测速后修订，不能提前写成已有性能。

论文原有结果可以用于回归，但必须核对原始数据、模型和交付口径。原题五份 Excel、DEM、完整代码与结果包需要从你们原工程补齐，现有题目和论文附件不足以替代完整可运行工程。

## 十三、应用价值和成果转化，建议这样讲

### 1. 首个落地场景：应急演练与救援队任务辅助

这是适合当前团队验证的起点：

- 导入某地区的地图与需求表。
- 使用救援队实际设备清单。
- 模拟需求突增、设备退出和落点不可用。
- 让调度人员完成方案选择与事件处理。
- 记录操作时间、错误和反馈。

价值可以落在可测量的问题上：

- 减少人工重新协调的工作量。
- 更早发现电池、充电或中继瓶颈。
- 提高任务和物资去向的可追溯性。
- 为演练复盘和资源配置提供依据。

### 2. 市场差异化要与现有产品认真比较

DJI FlightHub 2 等现有产品已经包含机队运营、任务和航线管理等能力，因此通用地图、航线展示和任务管理不宜作为独创点。[DJI Enterprise](https://enterprise.dji.com/flighthub-2?utm_source=chatgpt.com)

你们可以重点验证自己的应用定位：

> **面向救援物资保障，将箱件、异构机体、有限电池、中继服务和动态需求放入同一个可解释调度流程。**

后续竞争分析需要实测或核对具体功能，不能根据公开介绍的遗漏，断言现有平台不具备某项能力。

### 3. 可尝试的转化形式

- 面向救援服务商的调度模块。
- 面向无人机集成商的数据与任务规划适配。
- 面向应急培训单位的演练与复盘软件。
- 本地部署、维护和场景配置服务。

定价和市场规模暂作为待验证假设。建议先完成 3—5 次访谈，重点了解：

- 目前谁在排任务，使用什么工具。
- 哪类变化最容易打乱计划。
- 电池、充电、人员还是通信最常成为瓶颈。
- 现场能获得哪些数据。
- 哪些输出是他们真正会采用的。

这些证据会直接帮助你们决定功能优先级，也比未经验证的收入预测更能支撑创业可行性。

## 十四、给队伍讨论时，建议先定下这六件事

1. **主场景：**先做洪涝断路下的应急物资运输与通信保障。
2. **基础工程：**谁负责第一天跑通原代码、数据和检查结果。
3. **本届范围：**三页工作流、两种偏好、一种动态事件、可导出任务单。
4. **主创新：**优先做依赖关系驱动的动态修复；学习辅助搜索作为后续重点。
5. **验收证据：**用户换数据会重新计算，事件发生会改变计划，所有已确认方案经过检查。
6. **应用验证：**尽早让真实调度或救援人员试用一个演练流程，形成可记录反馈。

**第一版最值得追求的完成状态是：队友拿一份新的资源与需求表导入系统，能看懂方案、选择取舍、处理一次变化，并把任务单交给操作人员核对。**在这条完整流程上继续增加算法深度、地图能力和设备适配，你们的创新、工程实现和应用价值就能相互支撑。
