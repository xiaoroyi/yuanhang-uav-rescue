# RFC-012 未执行场景紧急需求插入

状态：implementation-branch，按本轮单人全栈授权实施，待A/B复核；保留0.1.0-draft与proposed，未代替人类批准。

Event联合新增demand.added。公共身份、时间、幂等与版本字段保持不变，payload严格为demand和cargo_items；分别引用Scenario的需求与逐箱结构，1至32个实物箱件，箱件数量必须等于required_quantity。不用增改数量掩盖缺失库存。

范围：整个场景尚未执行、effective_time_s=0、已有救援点、新需求ID和新箱件ID、mandatory=true。每个新增箱件必须available、位于基地、关联该新需求且物资类型一致。允许选择现有物资类型，输入质量/体积、优先级、相对场景零点的期望/硬截止。现有Scenario引用、时间、Schema和执行事实校验继续适用。新增救援点、在途插单或把箱件位置假设为无人机当前位置不在本次范围。

后端在同一事务追加需求与箱件、增加版本、保存不可变版本与Event、清除当前预约和active Plan；除非原输入为Mock，新增实物数据后data_origin改为user_input；其他字段保持。重复相同事件仅返回原回执，内容不同报409。非法输入报422并整体回滚。received_at仍由服务器写入。

Solver replan核对完整事件链与应用后快照，新增记录须与payload完全一致。此类事件明确使用全量求解，不能只修复原有任务而遗漏新增需求。新Plan绑定新Snapshot和父Plan；预算内无可行解时保留旧Plan作为历史，不冒充新版本可执行结果。

前端在事件类型选择“紧急需求插入”，表单显示现有点位、物资类型、箱数、每箱质量/体积、优先级和相对场景零点的截止分钟。提交前生成稳定的需求/箱件ID，展示实际库存增加；后台与算法校验通过后才显示新结果。新旧方案比较增加“新增已安排箱件”，旧机体/电池改派统计仅针对两版共有箱件，避免把新增箱件误计改派。

同一分支更新Schema、Mock示例、生成Pydantic/实际OpenAPI/TS、共享纯函数、后端事务、Solver能力、UI和测试。保留两种退出事件旧JSON。测试包括新旧记录不变、重复/冲突、ID/引用/类型/位置/数量/状态负例、执行事实/非零时刻拒绝、应用后payload破坏、真实Worker全需求覆盖、不可行新时限不发布旧Plan、刷新恢复与移动端表单。
