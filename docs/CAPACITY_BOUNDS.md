# 运输架次容量下界

入口为“事件复盘 → 资源分析与试算 → 运输架次容量下界”。它绑定当前所查看Plan的原Snapshot，场景后来编辑不会改变历史分析。展开可见质量、体积两种依据；“导出分析JSON”包含完整精确比值、箱件ID见证和数值规则。

这是完整服务所需运输架次的必要下界。对每项需求分别选足数量的最轻箱件与最小体积箱件，再除以基地可用运输机和兼容电池交集中的最大额定容量，向上取整并取两者最大值。两个见证可以不同，最大质量与最大体积也可来自不同机型，因此它是一项放松模型。超额库存不全部计入需求。

下界忽略路径、能耗、时限、整箱组合、充电、并发及通信，不能按与当前计划的差额推算增机数量。达到它不证明完整调度最优，也不证明整箱组合一定可行。Mock、已有执行事实、库存不足或无可用资源等情况显示“未评估”，不输出假0。无效Snapshot仍按现有契约拒绝。

独立容量检查使用math.fsum重建质量/体积，保留原1e-8kg/L容差；下界用同一binary64输入的精确分数，加4个向上相邻浮点值保护后向上取整。条件和兼容影响见[数值及接口RFC](CONTRACT_RFC_011.md)。

独立复现无需HTTP或数据库：

```powershell
.venv\Scripts\python -m solver.bounds --example compact --output evidence/solver/capacity-compact.json
.venv\Scripts\python -m solver.bounds --example contest --output evidence/solver/capacity-contest.json
```

可用`--scenario 路径`代替示例，输出不得覆盖输入。当前保存的默认32箱为4架次，原题80箱为10架次；这些是当前输入下的容量下界，不是完整任务最优答案。

专项检查包括独立位掩码精确装箱对照、必要下界严格小于装箱最优的例子、独立质量/体积见证、超额库存、资源退出、初始充电、数值整数边界、无效输入和历史Snapshot绑定。实际运行14项Python专项、1条真实浏览器流程通过；1440/1280/390截图已查看。后续全套结论见IMPLEMENTATION_STATUS，不沿用旧检查覆盖新代码。
