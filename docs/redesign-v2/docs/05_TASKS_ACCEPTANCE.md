# 05｜全量任务、依赖关系与验收标准

> 不按天安排。任务按依赖推进，低耦合模块可并行；一次交给 Codex 后，按任务板连续实施、测试、记录。本文是工作范围和完成门槛，不是对当前软件已完成情况的断言。

## 1. 实施原则：保留底层，重构任务流程

采用已有仓库的独立分支，优先增量替换页面壳、路由和视图投影。保留正常工作的 Solver、不可变快照、资源账本、事件幂等、验证与导出。没有代码审计前不决定“全部重写”。

先打通一条新的完整业务路径，再逐项补高级分析与执行能力；**不把每个页面都做成只有标题和占位卡片的假完成版本**。页面所有主动作应有真实实现、条件禁用或明确外部阻塞。

若现有代码已有同等能力，补测试与新入口而非重复实现。发现旧功能只有静态按钮或硬编码结果，先登记实际状态再修复。

A 为算法负责人；B/C 为系统线，分别主做前端和后端。单人全栈执行期间可以跨模块，但仍保持边界和可拆提交；后续恢复三人职责。

## 3. 每张任务卡必须写什么

`任务 ID / 目标用户动作 / 前置依赖 / 修改范围 / 输入输出与版本 / 主正常流程 / 错误与空状态 / 自动测试 / 浏览器证据 / 已知限制 / 实际状态`。

状态统一为 `todo / in_progress / review / done / blocked`。一个任务只有界面但服务不存在，应保持 in_progress；外部服务未配置不能把模拟成功当作实际done。阻塞项不应阻止继续做无依赖的其它任务。

## 5. 全链路验收故事：从空白新任务到复盘

这是最终核心验收，而不是仅使用内置历史方案展示。

1. 在干净浏览器打开根地址，落到首页；无说明即可找到“新建救援任务”。
2. 创建独立模拟任务，选择**不同于原题默认中心**的测试区域，设置基地和多个需求点；这些是合成业务测试数据，不声称实测。
3. 导入需求与箱件库存、选择异构机体和电池；制造一条兼容性错误，检查能够定位并修复。
4. 保存新版本，运行条件检查；未提供的模型能力明确显示，不自动全部通过。
5. 对同一个快照运行时间/能耗两个策略。结果可以相同，但必须实际运行且记录不同请求和实际目标。
6. 结果页点击一个需求点、一个架次、一块电池，地图、任务表、甘特和详情都联动到相同 ID；图表使用本次结果。
7. 确认方案，检查不是起飞；在“模拟执行”明确启动服务器演练。
8. 演练推进到一部分货物已送达、一架机仍在途中、另一架机未出发时暂停。刷新页面后状态与时间保持。
9. 在当前演练创建新增需求并把一架未起飞机设为不可用；事件幂等保存，新库存不足时明确缺口，不凭空新增箱件。
10. 运行重规划，检查已完成不撤销、在飞载货不换机、不重置 SOC、不可用机不接新任务。显示真实影响链与前后差异。
11. 确认调整，模拟适配器返回分设备应用状态；注入一台设备 ACK 超时，系统不得假装全机队同时切换成功。
12. 按可确认状态继续模拟，形成完成/部分完成报告，导出任务数据、资源时间轴、事件与变更记录。
13. 打开复盘，计划、模拟事实与原始观测来源清楚；导出重新导入后可重现同一事实和统计。

这条故事通过，不代表真机验证通过；但它能证明产品不是静态网页、回放动画或单个固定数模实例的包装。

## 7. 视觉验收不能只跑 build

Codex 必须启动实际前后端，用无扩展的测试浏览器检查。截图右侧浮动头像/工具若由浏览器扩展产生，记录为外部因素，不误删业务代码。

至少保存以下页面的1440×900与1280×720截图：有任务的首页、新建任务/数据错误、条件检查、**真实计算后的方案页**、选中架次的地形/电量分析、机体/电池甘特、进行中的模拟执行、事件前后差异、复盘与资源增配。必要时增加1024宽测试和长点名/大量数据情况。

先看截图再修：主动作是否可见、地图是否主导、文字是否拥挤、标签是否遮挡、是否有双重/多层滚动、图表是否截断、空白是否来自未完成服务。截图比较基线必须经过人工确认，不能把有缺陷的新截图自动接受。

可使用 Playwright 执行业务和截图测试。[S14] 记录实际命令和退出状态；浏览器工具不可用则明确未验证，不声称视觉检查通过。单元测试和截图都不能完全替代新用户试用。

## 8. 工程环境和依赖安装

检查当前Node/Python/包管理器和锁文件；使用项目虚拟环境与本地依赖，按现有正确技术栈实施。可安装需要的免费组件与测试工具，记录版本和用途；不要为了样式引入第二套完整UI体系、第二套状态管理或同时常驻两个地图引擎。

涉及管理员权限、系统服务、防火墙、收费服务、令牌、真实设备或删除现有环境时必须取得明确确认。不要使用来历不明的一键脚本、把密钥写入提示词或为了安装依赖关闭安全检查。

React/现有组件库负责表单与布局，MapLibre负责主地图，ECharts负责分析；这些是建议组合，已运行的同等库可保留。底图不依赖未经授权的大量缓存；字体文件不随本对接包分发。

## 9. 本轮要输出哪些证据

建议写入仓库 `evidence/redesign-v2/`，至少包括：

- `REPO_AUDIT.md`：实际源码、功能与工具能力；哪些只是截图判断。
- `API_MIGRATION_MAP.md`：旧新接口、字段映射与兼容测试。
- `FEATURE_TRACEABILITY.md`：F01—F28、R00—R24真实完成程度与证据。
- `TEST_REPORT.md`：实际运行命令、日期、环境、通过/失败/未运行。
- `VISUAL_REVIEW.md`：对应截图、问题、修复、再次检查。
- `SCENARIO_MANIFEST.json`：测试输入来源、哈希、规模、模型、版本。
- `EXECUTION_SMOKE/`：去敏的Plan/Job/Event/遥测/指令/模拟事实记录。
- `DEMO_GUIDE.md`：从新任务到复盘的用户操作，而非开发者内部命令清单。
- `KNOWN_LIMITATIONS.md`：缺数据/硬件/服务的具体能力，不能笼统写“后续完善”。
- `HANDOFF.md`：分支、提交、启动方式、剩余任务、继续工作的准确入口。

用户不需要再把同一个全量需求分十次重新描述；若Codex受上下文或执行时长限制，保存上述进度后可根据任务ID继续，不重复推倒重来。

## 10. 比赛展示与产品创新的统一叙事

建议演示按一个救援任务展开，而不是一页页罗列功能。内部视频可以用约5—6分钟编排，但这不是赛事官方时长要求，提交时仍核对实际规则。

叙事：新建需求→发现资源/环境问题→修正→生成可对比方案→地图/资源时间轴解释→启动模拟→事件影响和局部修复→资源增配或复盘。创新在用户动作中出现，不用“创新点”卡片代替证据。

材料中的速度、保障率和提升比例只能来自本版本实际实验；旧数模论文作为已有基础单列。截图里5站32箱与原题15站80箱不同，应分别标注，不能混用实验结果。

项目简表/说明书/原型源代码证明等按用户提供指南检查；PPT、视频和说明书保持相同数据与实际功能状态。检查匿名内容、个人路径、Office元数据、浏览器信息、仓库地址、密钥及地图/素材许可。AI辅助和来源按赛事要求如实披露，不编造客户合作或实飞证据。

## 11. 最终交付判定

“完成”指新首页与任务流程能操作、地图和结果图能反向定位实际数据、服务器仿真与动态修复能跑通、设备接口有可靠合同与模拟测试、原算法和导出没有退化，并提供准确的完成/阻塞记录。

不是代码行数、页面数量、卡片数量或一张漂亮截图。除非明确作为设计稿，任何“已成功、已送达、已接入、已验证、实时、AI”都必须能追溯到对应数据、执行或测试。
