# 01｜援航 V2 产品结构与逐页交互规范

> 本文为本轮重构的产品目标。代码和接口现状由仓库审计确认。新版替代旧规范里的首页、导航和“三个长页面”布局；保留原有真实计算、快照、验证和历史数据原则。公共技术资料见 `06_RESEARCH_NOTES.md` 的 S01–S27。

## 1. 截图诊断：问题不是“深色不好看”

| 截图/现象                                                    | 对操作的影响                                     | 具体重构要求                                                 |
| ------------------------------------------------------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| 072225：数据大屏首屏主要是巨大宣传区与统计卡，地图在下方     | 首页与工作页混杂，用户不知道下一步；大屏不是一屏 | 新增真正工作首页；大屏改为可选只读模式；业务页删除 hero      |
| 072237：结果未算时大段说明“不会用示例曲线冒充”，下方四张创新说明卡 | 无结果状态占满页面，技术自证替代实际操作         | 空态只给原因+一个下一步；创新以可点击诊断和对比结果体现      |
| 072247：场景、演练、题设数据、多处版本和入口混在一起         | 同一对象有多个称谓，新用户难辨全局与当前任务     | 顶层“救援任务”；内部数据仍可称 Scenario；资源模板与任务快照分开 |
| 072256：地图页先展示标题和四张卡，再出现地图，右侧突出资产 hash | 主要空间任务不在首屏，资产管理信息抢占操作空间   | 地图工作区即首屏主体；hash/CRS/来源放“数据详情”抽屉          |
| 072306：列表、策略、地图各有独立滚动，地图内控件和大标签较多 | 筛选、计算和地图阅读竞争空间，关键动作不明确     | 固定工作区；左列表、中央地图、右详情按需；计算按钮固定在准备阶段 |
| 072319：事件表单和多个保证说明，整体像另一个孤立页面         | 看不出事件属于哪次执行、改了哪个已确认方案       | 事件在执行上下文处理；复盘用于历史分析，不承担唯一事件入口   |
| 多图右侧浮动图标/人物头像                                    | 可能遮挡地图/操作，但可能来自浏览器扩展          | 先用无扩展浏览器确认归属；属于本应用才移除，不能凭截图乱删代码 |

正面基础也要保留：独立电池、需求与库存区分、来源标签、未评估状态和实际结果不伪造。这些是正确约束。**错误在于将实现说明反复铺在主界面上，而不是把它们做成清楚的状态、详情和阻断机制。**

截图中的 5 个需求点、32 箱、3 架运输机看起来是当前演练子集，不等于论文的 15 区、80 箱、8 架全量实例。重构后应显示“当前任务”数据，原题实例作为单独案例；是否子集由现有数据清单确认。

## 2. 产品定位与统一名词

对用户：援航是“无人机救援任务规划与运行协同系统”。用户需要知道：本次救援做什么、现有条件能否完成、推荐哪套方案、执行到哪里、变化后怎样调整。

不把所有模块都做成一个大屏，也不把任务页做成产品宣传页。品牌说明仅在“关于”和首页一行副标题出现。

| 用户可见名词  | 内部对象                      | 含义                                               |
| ------------- | ----------------------------- | -------------------------------------------------- |
| 救援任务      | Mission / operation aggregate | 一次具有区域、目标、资源、计划和执行记录的救援行动 |
| 任务准备      | Scenario draft                | 为本次任务编辑的输入；不是正在执行的事实           |
| 输入快照      | Snapshot                      | 一次求解使用的不可变输入                           |
| 调度方案      | Plan                          | 多架无人机、箱件、电池与中继的完整计划             |
| 运输架次      | Sortie                        | 一次具体飞行运输；不能与整个救援任务都叫 mission   |
| 运行/演练记录 | Execution                     | 按某方案执行的一次模拟、SITL或真机运行             |
| 方案回放      | Replay                        | 只读展示某方案或已录日志，不生成新实际事实         |
| 资源中心      | Resource catalog + ledger     | 机型、实体、箱件、站点、地图与保障设备的可复用记录 |
| 演练评测      | Experiment / test run         | 复制场景做扰动、方法对照和批量评测，不污染正式资源 |

屏幕中尽量使用中文业务名；`snapshot_id`、SHA、Schema 等放“技术详情”。对象 ID 仍可显示为次要、等宽小字，支持复制和检索。

## 3. 新信息架构：四个主要入口，设置与帮助放次级位置

全局导航：**首页、救援任务、资源中心、演练评测**；底部固定 **设置与接入** 和帮助。帮助不是同等业务模块。Logo 永远返回首页，页面明确有“首页”条目。

```text
首页 /home
救援任务 /missions
 ├─ 新建 /missions/new
 └─ 某次任务 /missions/:mission_id
     ├─ 准备 /prepare          区域与基地→需求与物资→机队与保障→条件检查
     ├─ 方案 /plans            计算进度、候选、比较、明细、确认
     ├─ 执行 /execute          演练/实际跟踪、事件处理、调整草案
     └─ 复盘 /review           计划对实绩、事件、瓶颈、报告
资源中心 /resources
 └─ 机体｜电池｜物资｜常用点位｜地图资产｜通信与地面保障
演练评测 /experiments
 └─ 案例库｜单次测试｜批量对照｜试验记录
设置与接入 /settings
 └─ 服务与离线包｜设备适配｜气象接入｜权限｜模型参数与许可来源
可选：只读态势大屏 /wallboard/:mission_id
```

任务的四个页签属于同一 `mission_id`。不能切换页签后丢失当前任务或默默换成默认案例。面包屑为“救援任务 / 名称 / 方案”，全局只出现一个任务选择器。

旧菜单迁移：数据大屏→首页+可选只读态势；场景与资源→任务准备+资源中心；地图与地形→准备中的区域编辑+资源中心地图资产；调度工作台→方案；方案对比→方案内比较；事件复盘→执行事件处理+复盘；历史档案→任务列表归档筛选；新手教程→帮助和首页首次引导。旧路由保留重定向或只读兼容，不让已有分享链接失效。

## 4. 一条完整业务路径

```text
创建救援任务
  ↓ 保存草稿
输入区域、基地、需求、库存和机队
  ↓ 条件检查（可提前反复运行）
修复缺失 / 明确选择模拟假设
  ↓ 冻结输入快照
生成候选方案（当前可行初解 + 限时改进）
  ↓ 看明细、比较取舍、必要时修改并重算
确认方案（只确认计划，不起飞）
  ↓ 执行前检查 + 选择运行类型
仿真运行 / SITL / 获授权的设备下发
  ↓ 实时跟踪 + 接收事件
评估影响 → 生成调整草案 → 对比并批准 → 分阶段生效
  ↓ 完成任务并核对交付
复盘、导出报告、归档
```

界面始终能回答：**我现在处于哪一步、为什么不能继续、点击哪里补齐、下一步会产生什么影响。**

不要把“计算方案”“确认方案”“上传设备”“开始执行”合并为一个按钮。可提供连续引导，但每一步语义和风险不同。

## 5. 全局设计系统与布局硬约束

### 5.1 视觉方向

默认使用清晰的浅色业务界面：中性灰背景、白色表面、深色正文、蓝色操作。地图可以使用自然地形或影像色；执行页可切换深色，但不是另一套布局。用户当前抱怨的是混乱和难读，不是必须把深色一律删除。

设计 token 建议（可微调但必须全站统一）：

```css
:root {
  --app-bg: #F3F5F8;
  --surface: #FFFFFF;
  --surface-subtle: #F8FAFC;
  --text-main: #172334;
  --text-secondary: #526276;
  --border: #DCE3EB;
  --action: #2563EB;
  --success: #18794E;
  --warning: #A95D08;
  --danger: #C43131;
  --unknown: #687688;
  --radius-panel: 10px;
  --radius-control: 6px;
  --space-unit: 4px;
}
```

正文14px、次要文字12px、表头12–13px、页面标题22–24px；工作台不用40px以上标题。数字采用 tabular-nums，重要单位不隐藏。可点击行40–44px高，按钮36–40px高，标题/数值都不能拥挤截断。颜色同时配图标、线型或文字，重要状态不只靠红绿区分。

组件库：沿用已有成熟组件库；缺失时优先采用 shadcn/ui 的 Sidebar/Tabs/Dialog/Sheet/Popover 等单一体系。图表统一 ECharts。不要同时新增 Ant Design、MUI、Element等不同视觉体系；不要照搬营销型 Dashboard 模板的 hero、收入卡与装饰背景。[S12,S13]

### 5.2 尺寸和滚动

- 首页/资源中心全局侧栏200–224px，可折叠为64px；任务工作台默认64px，留出地图空间。
- 全局顶栏56px；任务信息行48px；阶段页签40px；工作台工具条约40px。可合并小型状态，禁止再叠大标题和大号统计卡。
- 方案/执行页使用 `height:100dvh` 的壳体，内容 `min-height:0; min-width:0`；页面本身不出现长页面滚动。列表、详情、底部分析各自明确管理滚动，不套多层同向滚动容器。
- 左任务列表默认260–280px；右详情300–340px，未选对象时不占位。中央地图在右详情关闭时占主要工作区至少65%；右详情打开时允许缩小，但1280px屏幕不得挤成窄条。
- 1440×900 默认地图可见高度≥440px；1280×720 时收起底部图表和右侧详情，地图高度≥340px。高密度模式不是把字体缩成10px。
- 底部时间轴默认160–200px，可拖至280px或收为36px。右详情可折叠。1366及1280宽度必要时“列表/详情”互换，不能三栏硬挤。
- 1024px以下改为“地图 / 列表 / 详情”单区域切换；移动端支持查看与简单上报，不承诺在手机上完成所有复杂排程。
- 报告、长表格可纵向滚动，但不得把地图挤到首屏以下；表格只在自身容器横向滚动。
- 除地图库署名/比例尺和必要控制外，不在地图上放品牌口号、版本大卡、助手头像或重复模式说明。

### 5.3 文案整改词典

| 当前表达                                | 替换                                                   |
| --------------------------------------- | ------------------------------------------------------ |
| 让每一份现场信息，都有据可依            | 页面标题“任务准备”；副标题可省略                       |
| 让每一条航线，都有数据支撑              | 首页最多一句产品说明；业务页删除                       |
| 这里不会用示例曲线冒充算法输出          | “尚未生成方案”+“生成方案”按钮                          |
| 真实计算此策略                          | “按此偏好计算”或“生成方案”                             |
| 把方案拆到每架飞机、每次任务            | “机队排程”                                             |
| 从给出路线到给出可核验的资源计划        | 删除宣传卡；提供“查看约束检查”                         |
| 不可变快照→保存方案→独立重建约束        | “输入版本 vN · 检查已完成”+详情入口                    |
| 本地计算·模型内规划辅助（每个面板重复） | 任务顶栏一次“演练”模式；检查详情说明适用范围           |
| 本方案未评估通信                        | “通信未检查”；当通信为必需项时显示阻断及“补充通信配置” |
| 安全评分 98 分                          | 禁止没有校准依据的合成评分；改为具体检查与余量         |

提示分三级：阻断问题内联且有修复入口；非阻断警告一条摘要可展开；技术证据在抽屉。不能为了简洁把真实风险完全隐藏。

## 6. 页面 H：工作首页 `/home`

**用户问题**：从哪里开始？哪些任务正在进行？我上次做到哪里？

结构：顶栏；“救援工作首页”标题+“新建救援任务”主按钮；当前进行中的任务表；“继续上次任务”；资源与服务简要就绪状态；案例入口。无巨大插画/装饰3D。

首屏必须有三个明确动作：**新建救援任务（主）**、打开任务（次）、运行示例演练（次）。三个动作分别创建空草稿、打开列表、复制隔离示例，不得都导向同一个默认场景。

任务行字段：名称、运行类型、阶段、需求点数、未保障关键需求数、更新时间、当前负责人/无多人则省略、一个上下文动作。

上下文动作由后端状态给出：草稿→继续准备；检查有阻断→修复输入；方案运行中→查看计算；有候选未确认→查看方案；已确认→执行前检查；运行中→进入跟踪；已结束→查看复盘。

资源与服务简况不超过一行卡：可用/总机体、可用/总电池、地图包状态、设备连接状态。不能让“本机服务在线”被误解为无人机在线。

初次无任务：显示三步简短引导和“新建救援任务”；例子使用专门演练副本，不自动写入实际库存。

只读大屏：从当前任务菜单打开 `/wallboard/:id`，显示地图、关键需求进度、机队状态、当前事件，固定视口无导航/编辑表单；数据不足时显示明确状态。这不是主页，也不是首要开发阻塞项。

## 7. 页面 M：救援任务列表 `/missions`

按“进行中、草稿、已结束、归档”筛选；搜索任务名/ID/地区；列表模式为默认。提供创建、复制为演练、导入任务包、打开、归档。复制实际任务只能复制输入，不复制执行事实、授权或占用锁。

每个任务独立保存输入、计划、执行与报告。删除有执行记录的任务默认不开放，使用归档；需要删除时权限与确认分离。批量操作不得启动设备。

## 8. 页面 N：新建救援任务与准备工作区

### 8.1 新建只问少量核心信息

首个对话框或整页输入：任务名称、运行类型（默认演练/规划辅助；真实控制只有具备权限与接入才显示）、计划起始时间及时区、任务区域。空白创建、使用模板和导入既有文件三种入口。

创建后进入 `/missions/:id/prepare`，四步在同一工作区完成。保存为草稿不要求全部字段齐全。切换步骤不丢失尚未提交的本地编辑；退出前提示未保存。

### 8.2 第一步：区域与基地

主体地图约70%，左侧表单约30%。用户搜索地点、输入坐标、地图点选基地、画任务区域；创建需求点可在下一步完成。

必填：区域/活动范围、至少一个起降基地及坐标、起始时间。地图来源可先为可用底图，但实际净空检查必须有合适计算资产。导入数据要让用户确认坐标系，而不是猜测。

显示可用地形资产和覆盖结果，用简明“已覆盖/部分覆盖/缺少高程”状态。点击可查看分辨率、时间、CRS、垂直基准、NoData；hash放折叠技术区。

可绘制风险对象：空域限制、投送点不可用、地面风险、障碍。创建时必须选对象类别；洪水图层不自动变成禁飞区。撤销/重做只改草稿，保存后创建数据版本。

地图任意点可右键/长按打开“添加需求点、添加备降点、测距、查看位置”，不能直接“飞到此处”。

### 8.3 第二步：需求与物资

左侧需求清单，地图为主体；可切换下方库存表。不让用户一次面对六个同层tab加另一组资源tab。

需求表单：需求点、物资类别、需求数量/单位、优先等级、必须保障数量、期望交付时间、硬截止（可无）、投送方式、接收条件及联系人（按权限显示）。支持批量导入CSV/Excel与逐行错误。

库存表：箱件ID、类别、质量kg、体积L、仓库、可用状态、适用投送/温控要求、有效期（可选）。箱件与需求分开，允许未绑定某一需求的库存；已有 `cargo_item.demand_id` 不得直接删掉，需通过分配模型迁移。

界面同时显示“需求、可分配库存、计划已分配、实际已交付”。数量相同不等于对象相同。关键箱件不可拆；临时需求不意味着物资自动增加。

选需求点→地图定位并打开现场信息；选箱件→看其仓库、可服务需求和已计划架次。地图标签只显示站点简称，不将多个地名拼成遮挡画面的长条。

### 8.4 第三步：机队与保障

从资源中心选择本次可用的真实实体；演练可使用隔离副本。不要输入“C型2架”后自动生成不存在的实际机体。

机体：型号、位置、可用时间、健康/维护状态、载荷与投送能力、当前已装电池、执行状态。电池：实体编号、兼容型号、SOC、SOH、容量定义、位置、充电/可用时间、温度（有数据才显示）。

保障：起降位、装卸工位、充电端口/功率、中继机/能源组件、地面网关、接收点服务时间。高级配置默认折叠，但一旦启用约束，必须实际进入计算。

库存/调度冲突显示“某机体在另一个任务被预约到xx”；不允许跨任务双重确认。模拟资源与实际资源用命名空间隔离。

### 8.5 第四步：条件检查

页面标题“条件检查”，主动作“运行检查”。按地图覆盖、需求/库存、设备/电池、天气、通信、起降/落点、执行许可记录分组。

每项返回：通过、需关注、阻断、未知、未启用；带影响对象、发生时间窗、来源、新鲜度和可点击修复动作。示例文案使用真实结果占位：“S003 缺少接收方式，暂不能安排投送”而非“系统存在异常”。

预检只检查当前输入完整和必要可行条件，不能宣称整个复杂任务一定可行。此阶段可显示单箱/单点能力矩阵，但不存在完整Plan时不显示完整运输结果。

模式规则：

- 演练可使用显式假设并保存在快照里，例如人工风情景；不能把缺少气象默认记为真实良好。
- 规划辅助允许生成带缺项说明的方案，强制模型项仍不可跳过。
- 真机执行需要单独的执行前检查与设备状态，不以这里的通过替代。

底部固定“返回修改”“保存检查结果”“进入方案计算”。有阻断时最后按钮禁用并说明第一处阻断；未知但非必需项可有说明地继续。不能通过“忽略全部”绕过硬约束。

## 9. 页面 P：方案生成、比较与详细调度

### 9.1 空态和计算入口

进入方案页没有结果时，主体仍显示任务地图和已输入需求；右侧为紧凑“生成方案”面板：偏好、保障要求、计算预算、模型范围、可选稳健配置。默认只展示已支持的策略。

时间/能耗/费用/均衡属于决策偏好；CPU时间预算是另一参数，不能混为“快/慢运输”。费用无有效价格时禁用“费用优先”，不把能耗乘任意系数当人民币。

主要按钮固定“生成方案”；次要“比较多种偏好”创建同快照的多次求解。点一次后保存Job，刷新页面可继续查看。

计算中展示真实阶段（预处理/构造/改进/检查）、耗时、预算、当前候选数和取消。没有真实百分比就用不定进度，不展示随时间自动涨到99%的假百分比。有已验证初解时允许先看，但仍显示改进进行中。

### 9.2 有结果时的标准工作区

```text
全局顶栏：援航｜任务名称｜演练/规划/设备跟踪｜服务与连接
任务页签：准备  /  方案  /  执行  /  复盘
方案工具条：方案选择｜检查摘要｜计算/继续改进｜比较｜导出｜确认
左：需求/架次列表       中央：主地图                 右：所选对象详情（可关）
                        选中航路、投送点、风险区
底部：机体排程｜电池与充电｜需求保障｜航段剖面（按需切换）
```

最多保留一条紧凑指标行：关键保障x/y、最后交付、全队返航、总能耗/费用、未满足需求、检查摘要。无结果用“待计算”，不把每个字段做成大卡片。

左侧默认“需求”；切换到“架次”看具体飞机安排。筛选关键、未保障、迟到、有警告、机型、机体；选中跨地图/表格/甘特同步。箱件明细进入需求或架次抽屉，不默认展示32个原始箱号挤占首屏。

### 9.3 最终方案必须给到的业务输出

- 方案总览：范围、策略、保障情况、主要代价、未保障原因、验证范围、计算预算/状态。
- 逐架次：机体、机型、电池/能源组件、准备/起飞/逐站交付/返航、载荷、路线、能量和余量。
- 逐需求：需求数量、计划保障数量、首批基本保障时间、全部满足时间、缺口、预计/实际区别。
- 逐箱件：源仓库、计划架次、去向、预留/装机/在途/签收状态。
- 逐资源：机体和电池分别的使用、充电、等待；中继和地面端口同理。
- 约束问题：能定位到地图位置、对象、航段和时间的清单。

确认按钮只确认当前方案并建立预约；已过期快照时不可确认，提供“基于新输入重算”。确认后可去执行前检查，不自动飞行。

### 9.4 方案比较

在同一任务内打开比较抽屉或子路由，最多并排2–3个方案；同时提供“推荐理由”和未被满足的需求。选择推荐方案必须有可解释规则，不能固定给第一张卡加“AI最佳”。

比较分三种，明确标题：

1. 同条件策略比较：同输入快照、同必须保障集合、同模型范围；比较偏好差异。
2. 条件变化前后：不同快照，首先列变化条件，再比较结果。
3. 算法实验比较：同数据与预算的不同方法，在演练评测里完成。

时间—能耗散点可用；只有2个候选就显示2点，不拟合虚假的完整帕累托曲线。雷达图不是默认主比较图；归一化目标必须公开固定基准。

## 10. 页面 E：执行跟踪与中途变更

### 10.1 三种运行入口要分清

- **方案预演**：只读播放已有计划，不产生业务事实，不测试扰动后真实状态。
- **仿真演练**：后端仿真引擎推进状态和事件，真实执行本地计算逻辑；写入隔离的 simulation execution。
- **设备执行**：SITL或已支持真实设备，经权限、设备绑定和执行前检查后下发。UI始终区分SITL和真机，不将二者都简称“在线”。

入口页展示本次运行类型、计划版本、参与机体、电池装载/物资准备、地图天气有效性及设备状态。默认提供“启动仿真演练”；真机未连接时设备按钮禁用，不能弹假成功。

### 10.2 执行工作区

布局与方案一致，顶部突出运行类型和时钟；地图居中；左侧机队列表；右侧选中机体遥测/任务/物资；底部实际与计划时间线。策略面板从常驻位置退出，改为“调整计划”动作。

单机最重要信息：当前阶段、位置、SOC、当前箱件、下次交付ETA、航向/速度/高度及基准、遥测最近更新时间、链路状态、执行中的计划版本。无需默认摆满RPM/云台/姿态等与运输决策无关指标；可在设备详情里扩展。

全队指标区分：计划已分配、模拟已交付、人工确认已交付。运输完成通常需要签收或载荷证据，不能根据图标到达站点直接自动核销实际物资。

报警集中在一个可过滤事件队列：严重程度、对象、时间、当前影响、处理建议和确认人。确认阅读不等于故障解除；重复事件合并显示次数，不连续刷屏。

### 10.3 中途调整的完整交互

入口：执行页“上报变化”或点击机体/站点/天气事件。可记录：机体或电池不可用、新需求、落点不可用、禁飞/风险更新、天气窗口变化、交付延误。

事件表单先显示对象与当前状态，不能将飞行中的机体用“未起飞故障”处理。事件受理后：

1. 当前已确认方案仍保留，受影响部分标记需重新检查。
2. 自动/手动启动影响分析，显示直接与连带受影响任务。
3. 创建调整草案，列已完成/在途承诺/可调未来任务。
4. 生成候选修复；地图虚线旧计划、实线新计划，实测轨迹另用统一样式。
5. 查看哪些箱件改派、哪些仍由当前机体运送、谁延迟、资源是否足够。
6. 操作员批准后才进入下发/生效过程；纯模拟可在隔离执行器里应用。
7. 设备端受理与实际生效分别更新；部分机体失败时不能宣称全队已切换。

UI必须支持“暂不采用、继续改进、限制修改范围、保留某个已承诺任务、转人工处理”。不能只有“接受系统新计划”一条路。

“暂停排程”和“暂停某架无人机”使用不同按钮和说明；全局暂停仿真不会发送真机指令。真实操作不提供显眼的停止电机/急停快捷按钮，常规平台控制范围见接口规范。

## 11. 页面 R：复盘与调度分析

复盘不是宣传卡。按“任务结果、执行偏差、资源效率、事件影响、检查证据”分组；首屏给本次运行的计划对实绩和主要异常，不把原论文所有图一口气堆出来。

计划-only且没有执行时，标题“方案分析”；有模拟运行时“演练复盘”；有真实事实时“执行复盘”。三者数据来源必须可见。

主要模块：机队与电池甘特、需求按期/基本保障阶梯图、单架次高程/载荷/SOC剖面、通信来源时间轴、能耗分解、事件变更前后、资源瓶颈和增配试算。具体字段和论文图映射见02文档。

导出：任务单CSV/Excel、结构化JSON/GeoJSON、简洁运行报告、图表数据、完整实验证据清单。报告中包含场景/方案/运行ID、模型/版本、数据来源和限制。无人机航线专用格式只在适配器确实支持并通过导入测试后提供，GeoJSON本身不是飞控任务文件。

## 12. 页面 A：资源中心

资源中心是长期资料管理，不是每次任务必须从头走的入口。区分型号模板和设备实体；地图原件与处理产物；物资类型与实际箱件；站点模板与本次可用性。

表格全宽、固定表头、搜索、筛选、批量导入、修改审计；详情用抽屉。危险操作需确认，有被当前任务引用的数据不可无提示删除。更新资产后既有快照仍指向原版本，不自动改写历史计划。

地图资产页提供上传、预处理进度、覆盖预览、质量结果、加入可用资产、任务绑定、离线包管理。任务准备只需“选用资产/查看覆盖”，无需在主地图常驻原始hash。

## 13. 页面 X：演练评测（用户在哪里运行测试）

明确提供两个入口：**单次演练**和**算法对照实验**。普通用户不必找命令行。

单次演练流程：选择案例或复制任务 → 设置机队/需求/天气/故障 → 查看变化摘要 → 运行检查 → 计算 → 启动仿真 → 看结果。拥有随机seed及重置按钮，清楚地标记模拟数据。

案例库至少包括：小规模入门、原题回归、资源不足、部分电量/电池排队、地形/限制区、通信中继、天气改变、在途插单、遥测断流。基准实例来自论文资料但必须运行当前求解器，不能只打开一张历史图。

对照实验可选方法、预算、seed集合和事件序列，提交后台实验Job；结果列可行率、关键需求保障、完成时间、能耗、修复时间、改派量等。预先定义口径和失败处理，允许导出原始日志与配置。资源不足导致部分保障应另表，不与完整保障方案直接称优。

## 14. 设置与帮助

设置只负责默认偏好、接口配置、运行环境、权限、数据包、模型版本；不成为放不下的业务垃圾箱。常见设置展示说明和连接测试；secret不回显完整、不写前端构建产物。

帮助提供一条入门任务路径，以及当前页面的简短上下文帮助。新用户首次可引导“新建—填条件—检查—生成—演练”，随时跳过且不会每次打开反复弹出。

## 15. 前端架构重构原则

可沿用已有 React/Vite/TypeScript；不为本设计改成Next.js。建议模块：`app-shell`、`missions`、`resources`、`experiments`、`map-workspace`、`timeline`、`object-inspector`、`query-client`、`execution-stream`、`design-tokens`。

服务端数据（任务、Plan、Execution、Job）通过查询层管理；临时选择、面板、地图视角、播放时钟是前端视图状态。不要把所有数据放进一个全局大对象；不要复制一套库存数据到每个页面。

共同选择状态至少包括 `mission_id, plan_id, execution_id, selected_object_type, selected_object_id, selected_sortie_id, current_time, time_source`。同一个ID贯穿地图/表格/图表；播放快照切换时清除不再存在的选择，不误选同序号对象。

任何页面都要实现 loading/empty/error/partial/stale/ready。失败可以有保留上次结果的视觉状态，但不得把旧结果标为本次成功。

## 16. 本轮用户验收问题

第一次打开不用讲解，能否30秒内找到新建任务和演练入口？能否知道当前任务名称和所处阶段？能否在首屏看到主地图和关键动作？能否点击一个需求点查清送什么、谁送、何时送、当前缺什么？能否分清当前看到的是计划、模拟还是实际？能否从一个风险直接跳到修改并重算？

上述时间为可用性测试目标，不是已测结论。视觉与业务均通过才算本轮完成，不能仅用 `build success` 验收。
