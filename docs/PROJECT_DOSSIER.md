## 1 项目概述与使用场景

### 1.1 项目定位

项目全称建议保持为“援航——面向灾害应急的无人机运输与通信协同调度系统”。当前软件是一套在Windows本机运行、支持离线计算的调度决策支持与业务演练系统。它把地图、需求、逐箱物资、异构运输机、独立电池、地面保障和通信中继统一到可追溯的输入快照，计算具体到箱件、架次、机体、电池和时刻的安排，并提供独立约束检查、方案比较、模拟执行、变化处理和复盘导出。

它已经具备真实前后端和真实Python求解链路。用户修改有效输入后会产生新版本、新快照和新计算，不是只改变地图标签，也不是把论文答案作为固定返回值。当前执行模式是服务器业务仿真；没有连接真实飞控、没有完成SITL，也不是获得适航、无线电或空域许可的实飞控制系统。

### 1.2 业务背景

面向县域洪涝、山地断路等道路受阻情景，救援点分散，饮水、食品、医疗等物资需要按时抵达。设备数量有限，不同机型的载重、容积、速度和能源能力不同；同一机体可能轮换多块电池，返航后机体与电池也不会同时恢复可用。山区地形既改变爬升能耗，也可能遮挡网关链路，因此运输安排和中继服务不能各自独立绘制后再简单拼接。

项目回答四个实际问题：现有物资和设备能否完成输入需求；每架无人机何时运哪些箱件、访问哪些点、使用哪块电池；条件变化后哪些未来任务受影响、如何保留已发生事实并调整；资源紧张时增加什么资源以及在当前模型下有什么变化。

主要使用者是调度人员、物资与设备保障人员、算法研究与演练评测人员。当前部署没有多用户身份认证和角色权限平台，左下头像仅为本浏览器的姓名、团队、职责与配色设置。

### 1.3 当前范围

核心范围是单基地、不可拆箱、完整需求保障、确定性题设物理、异构机体与独立能源周转、地形净空、静态限制区、可选地面容量、可选通信协同，以及运输模式中的受控动态修复。默认小场景为5个需求点、32箱；保留15个需求点、80箱的原题输入和联合通信案例。模板每次创建独立输入，随后仍需真实求解。

不在当前完成范围内的内容包括：居民公共通信业务、多基地和移动补给车、完整多机四维避碰、实测风场与动力学、真实飞控、学习模型训练、完整概率鲁棒优化和航片自动建图。这些不是从任务板删除的功能，而是待继续研究或依赖外部条件的工作。

## 2 原有研究基础与本项目新增工作

### 2.1 数学建模基础

原题与论文提供单基地救援运输的模型、15点80箱数据、三型8架运输机、14块同型兼容运输电池、2架专用中继机和6套中继能源组件，以及DEM、链路参数和历史提交结果。研究主要分为四部分：

| 研究部分 | 原问题 | 当前继承方式 |
|---|---|---|
| Q1单点运输 | 每批仅访问一个点，确定安全载重与箱件组批 | 单点能力诊断、有限计数枚举与动态规划、余量敏感性 |
| Q2运输排程 | 多点架次、实体机体与共享电池、时间和能源取舍 | 当前运输求解器、双资源时序、完整逐箱安排 |
| Q3通信协同 | 地形影响下的直连与单中继两跳、驻点与能源轮换 | 当前有限候选联合排程、连续时间覆盖重建与中继展示 |
| Q4资源配置 | 冻结同版Q3任务及通信来源后划分专属资源组 | 冻结任务分区、并发峰值、共享损失和库存缺口分析 |

资料在`references/modeling/`，论文为`paper.pdf`，答案为`answers.xlsx`。历史数值只作为研究与回归参照；当前计划必须由当前快照重新计算并通过独立检查。不能要求短预算启发式逐位复现历史长时间搜索的最好结果。

原题适配器将原表中的箱件映射为单箱需求，保留医疗与首箱硬截止，并保留每箱质量、体积和原点位归属；通用用户输入则允许一条需求对应多箱实物。不能把“原题80箱”误写成“系统最多80条需求”，也不能把所有物资统一改成无硬截止。

### 2.2 新增的工程与产品工作

本项目将数模研究转为可替换输入的软件：统一契约和类型、严格导入、不可变快照、独立求解进程、版本与幂等、确认预约事务、动态事件、保留承诺的执行残余重排、模拟账本、设备状态读回、任务工作空间、地图与表格联动、真实三维与剖面、通信空间采样、资源试算、实验记录、导出与本机备份。

算法层新增或产品化的重点包括限时多起点可行构造、有限路线池改进、机体与电池资源依赖传播修复、静态限制区绕行、通用GeoTIFF绑定、地面容量约束、人工气象作业资格和释放下界处理。不能将所有原论文算法都写成本项目从零首创，也不能把通用地图、表格和后台组件称为独有技术。

## 3 当前功能与完整操作流程

### 3.1 产品入口

全局导航为首页、救援任务、资源中心、演练评测；设置和帮助为次级入口。任务内部按“任务准备、方案规划、执行跟踪、复盘分析”四阶段组织。首页展示应用场景、运输通信协同示意、实际模板规模、算法依据和操作入口，动态背景可以关闭，也遵守系统减少动态效果设置。

| 区域 | 已有功能 | 主要输出或依据 |
|---|---|---|
| 任务准备 | 区域基地、需求物资、机队保障、条件检查；草稿、模板、导入预览与保存 | 版本化Scenario和持久PreflightReport |
| 方案规划 | 实际计算、三种偏好、进一步搜索、同条件比较、检查与确认 | 绑定Snapshot的Plan和Validation |
| 调度安排 | 独立表格、逐架次/逐箱/中继/通信/资源、筛选搜索、详情与导出 | 当前Plan原文；六工作表Excel和CSV |
| 地图与地形 | 地点角色、实际路线、限制区、选中联动、卫星切换、DEM曲面与升降剖面 | 原始DEM与实际阶段分析 |
| 通信协同 | 中继安排、服务时段、双跳关系、指定高度空间采样 | 连续窗口检查与单独离散空间报告 |
| 执行跟踪 | 服务器时钟、暂停与倍速、运输与返航状态、每机后续任务、事件和候选差异 | 持久事实、实际生效排程和模拟遥测 |
| 复盘与资源 | 计划对模拟交付、任务变更、资源占用、反事实试算、只读档案 | 账本事实、冻结输入及独立计算 |
| 演练评测 | 策略、搜索、执行残余修复方法对照；取消和原始结果导出 | 同条件独立快照、真实Worker、完整成功失败记录 |
| 使用帮助 | 分章节图文、约38秒实际操作短片、字幕、术语与页面跳转 | 本项目真实截图与录屏 |
| 首页与案例 | 全宽动态地形首页、四类有来源演练、本机任务资产与输入复用 | 真实DEM、数据库计数、创建来源和独立任务 |
| 算法引擎 | 标准与EOH可选、本地策略导入导出、同输入引擎对比 | 策略包版本/SHA256/来源/实际评分调用数 |
| 接入中心 | 已安装模拟适配器、实际接口目录、OpenAPI与配置导出 | 当前模式与设备状态如实读取，不自动连接真机 |

### 3.2 新用户走通一次任务

1. 从首页新建任务。首次建议使用小规模运输演练；要看中继可以选择协同演练。空白任务需自行补齐输入。
2. 依次填写或导入区域基地、需求物资、机队电池与保障。DEM需绑定到场景；卫星图只是观察底图。
3. 运行条件检查，处理阻断项。步骤打勾表示当前填写或检查状态，不表示已经得到可行计划。
4. 保存有效输入并开始计算。后台创建不可变快照和Job；进度显示实际阶段、已用时间与候选数。
5. 在规划地图查看路线，进入独立调度安排表核对每箱、每架次、访问顺序、时间、电池与能源；地形与通信页查看相应证据。
6. 如需取舍，在同一快照和相同目标规则下计算不同偏好。结果可能相同，系统不能为了区别卡片编造差异。
7. 确认通过检查且没有过期的方案。确认只记录计划与预约，不代表已经上传设备或开始执行。
8. 创建模拟实例并开始演练。服务器推进时间和事实；页面动画只展示这些状态。
9. 运输模式下暂停，提交可支持的变化，查看影响，生成新候选，对比差异后采纳。已交付和已开始架次保留。
10. 查看复盘、安排表与资源时序，导出结果或执行档案。只读回放不会产生新交付。

执行中的联合通信方案当前可查看和模拟，不能进入尚不支持的在途联合修复。已有ready/running/paused执行实例的任务不能用普通“确认方案”覆盖预约，必须走执行调整或新建副本。

## 4 系统架构和技术栈

### 4.1 架构

```text
浏览器任务工作空间
  React 页面、MapLibre地图、ECharts图表、Three地形、表格与甘特
                          ↓ HTTP / SSE
FastAPI 业务服务
  任务草稿、输入校验、版本快照、Job、确认、执行、事件、档案、导出
             ↓ SQLAlchemy/SQLite           ↓ 独立Worker子进程
  版本与计划、预约、模拟账本                纯Python Solver
  指令与模拟设备状态                         空间与物理 → 候选 → 排程 → 独立检查
             ↓                               ↓
  runtime 数据与内容寻址DEM              JSON Outcome / Plan / Diagnostics
```

算法不导入后端或访问数据库，前端不重新实现一套业务能耗与SOC。后端负责身份、版本、权限边界和生命周期；Solver负责声明模型内的计算；独立检查器从冻结输入重建关键约束。分析读取Plan原Snapshot，不能拿当前已修改的场景替换历史输入。

### 4.2 技术栈

| 层 | 实际使用 | 用途 |
|---|---|---|
| 前端 | React 19、TypeScript 5.9、Vite 8、TanStack Query、Radix、Tailwind/CSS、Lucide | 严格类型界面、服务状态、统一组件与图标 |
| 可视化 | MapLibre GL JS、Apache ECharts、Three.js、Motion、Radix Colors | 二维地图、分析图、真实DEM曲面和适度动效 |
| 后端 | Python 3.11/3.12、FastAPI、Pydantic、Uvicorn | HTTP、严格DTO、流与静态前端托管 |
| 存储 | SQLAlchemy、SQLite WAL、JSON工件、内容寻址资产 | 本机持久化、版本、并发写事务和追溯 |
| 计算 | NumPy、SciPy、OR-Tools CP-SAT、PyProj、Shapely、Rasterio、Numba | 数值、有限优化、坐标/限制区/地形/通信计算 |
| 输入输出 | openpyxl等 | JSON/CSV/XLSX输入、Excel安排表、报告与归档 |
| 检查 | pytest、Node单测、ESLint、TypeScript、Playwright | 模块、契约、构建与真实浏览器流程 |

确切版本以`requirements.lock.txt`与`frontend/package-lock.json`为准。当前没有Redis/Celery、Kubernetes、PostGIS或云对象存储依赖；主要计算使用CPU，不要求4090。技术栈版本在本文基线中核对，不代表未来最新版本。

## 5 数据对象与不可破坏的不变量

### 5.1 对象关系

| 对象 | 职责 | 与其它对象的关系 |
|---|---|---|
| Mission | 面向用户的救援任务与四阶段生命周期 | 关联当前Scenario、已确认Plan与执行实例 |
| MissionDraft | 可以不完整的准备草稿 | 不能假装是已通过完整校验的Scenario |
| Scenario | 基地、点位、需求、箱件、机型、实体机、电池、策略及扩展 | 保存修改增加state_version；保留历史版本 |
| Snapshot | 一次计算的不可变完整输入、版本与内容hash | 嵌入Scenario；Plan与Job绑定它 |
| SolveJob | 异步计算请求、预算、进度、状态和错误 | Worker读取冻结输入，完成后关联Plan或准确失败 |
| Plan | 逐架次、逐箱、时序、能源、检查与算法范围 | 不覆盖旧Plan；不能跨Snapshot任意拼接 |
| Event | 尚未执行场景的零时刻事件 | 应用后生成新Scenario版本，再replan |
| Execution | 独立业务模拟实例、当前排程来源和事实游标 | 可同时保留旧承诺与新未来Plan，不能拼成伪造单Plan |
| ExecutionFact | loaded、delivered、资源释放等追加事实 | 交付数量与承诺来源，幂等去重、保留原文 |
| ExecutionEvent / Repair / Command | 执行变化、影响、候选、采纳与设备状态 | 与零时刻Event分开，使用revision、游标和幂等键 |
| Experiment / Archive | 独立对照与只读复盘 | 不自动确认、不控制原任务、不写交付事实 |

需求与实物库存分开。Demand表示某点需要什么、需要几箱、优先级和时限；CargoItem是有独立ID、质量、体积、位置和状态的不可拆箱。需求可由多架次分批满足，同一个实物箱不能重复分配。当前正式规划要求完整需求保障，`allow_partial_service=false`，未实现可发布的部分保障模式。

### 5.2 单位和时间

经纬度采用WGS84，顺序固定为`[longitude, latitude]`。质量kg，体积L，高度和距离m，速度m/s，能源kWh，SOC与SOH均为0到1。相对任务时刻用秒，绝对时间必须带时区。界面可以显示百分数和时分秒，但导出和接口保留明确单位。空值表示未知或未产生，不得显示成零。

机体、电池、中继能源是不同实体；机体释放不等于电池补能结束。资源区间采用左闭右开语义`[start,end)`，同一时刻先释放后占用。Scenario版本、Mission修订号和Execution修订号不是同一个计数器。

### 5.3 一致性规则

输入变更后保存新版本，旧Plan仍只解释原Snapshot；确认时检查版本与输入hash。相同幂等键和相同请求读取原回执，不重复产生副作用；相同键不同内容返回冲突。计划确认与预约变更在同一事务中完成。执行事实追加，不因新计划而把已交付物资恢复成仓内库存。

数据来源区分`mock`、当前Solver输出、导入历史等。Mock只用于明确标注的结构或界面开发，不能改标签充当当前计算。执行档案的校验和证明一致性，不是数字签名或真实来源认证。

## 6 地图输入与空间模型

### 6.1 地图层分工

地图底图用于定位与观察；DEM用于地形高程与净空；基地和需求点承载业务位置；限制区定义静态禁入范围；天气和通信层展示各自模型信息。卫星照片不提供可直接用于净空计算的高程。原镇龙乡HTML地图是地理数据展示，并不等于一套已准备好的卫星影像。

默认使用本地地形和地理上下文，断网仍可展示路线。在线卫星由用户主动启用，保留来源署名，失败时降级。需要外网不等于求解依赖外网，也不保证所有区域或网络下影像都可获取。

### 6.2 DEM资产

支持单波段、有CRS、米制高程的GeoTIFF。当前上传上限16MiB、源和准备栅格上限200万像元；这些是当前实现限制，可在确认需求后调整。北向EPSG:4326保留原网格，其它支持的水平CRS和旋转网格通过Rasterio准备，采用最大值高程与独立NoData掩码传播，不用平滑掩盖未知区。

归一化资产保存在`runtime/assets/<SHA256>.npz`，来源文件单独保存。Scenario记录资产ID、完整hash、水平CRS和声明的垂直基准。先注册资产、再绑定并保存版本；不能在求解期间原地换栅格。高程基准未知时不能擅自做椭球高与海拔转换。

完整DEM包包含清单、准备栅格和源GeoTIFF，交接时可以保留准确hash；单独复制场景JSON不会自动带走二进制资产。包导入检查路径、大小、数组头、hash和源数据重算一致性，不直接无约束解压。

### 6.3 净空与限制区

水平距离按WGS84测地线和实际折线路径累计。地形查询将测地航段细分为最长20m的弦，并用闭像元supercover取接触到的全部像元最高值，角点或边界接触也纳入。路径出覆盖区或接触NoData时，不能标为地形通过。

静态限制区采用基地中心的局部等距方位投影，受基地100km范围等条件约束。缓冲后用可见图生成有限绕行候选，最终按测地弦复查；边界和缓冲区均禁入。当前支持单外环多边形，不支持任意孔洞、多多边形或动态四维空域。有限图未找到路径返回未确定/输入未就绪，不当作真实三维空间无解证明。

## 7 运输物理和能源模型

### 7.1 模型来源与符号

当前`contest_transport_v1`和`contest_two_stage_v1`继承题设简化模型，代码在`solver/physics.py`。它们适用于本项目演练与算法比较，尚未经真机能耗日志标定。

| 符号 | 含义 | 单位 |
|---|---|---|
| d、H、Δh↑、Δh↓ | 实际航段距离、巡航高程、爬升、下降 | m |
| m、M、m₀ | 当前剩余载荷、额定载重、机体空质量 | kg |
| R₀、R₁、Eref | 空载/满载参考航程、参考电量 | m、m、kWh |
| v、v↑、v↓、η | 水平/爬升/下降速度、爬升效率 | m/s、无量纲 |
| C、q、s、ρ | 电池额定容量、SOH、出发SOC、最低返航SOC | kWh、无量纲 |

### 7.2 真实升降与时长

基地工作高度为地面高程；需求点工作高度为地面高程加服务高度，默认30m。每个航段的巡航高度取沿路最高地形加净空与两端工作高度的最大值，默认净空50m，但实际读取当前机型参数：

$$H = \max(H_{terrain,max}+h_{clearance},\ z_{start,work},\ z_{end,work})$$

$$\Delta h_{up}=\max(0,H-z_{start,work}),\quad \Delta h_{down}=\max(0,H-z_{end,work})$$

$$t_{leg}=(d/v+\Delta h_{up}/v_{up}+\Delta h_{down}/v_{down})\,k_t$$

每个访问点后按下一航段重新升降，不是一条贴地直线，也不是所有航段统一一个全局高度。`k_t`为明确的飞行时间压力倍率。准备时长为机型固定准备加每箱装载时间，交付时刻取停靠交接完成时刻；同次停靠的箱件共享该交接完成时间。

### 7.3 载荷相关能源

去程每段使用当时尚未交付的载荷，卸货后减少，回基地段为空载。以载荷比构造等效航程：

$$R(m)=R_0-(R_0-R_1)(m/M)^{1.5}$$

$$E_{leg}=k_E\left(E_{ref}\,d/R(m)+(m_0+m)g\Delta h_{up}/(\eta\,3600000)\right)$$

这里`g=9.81m/s²`，3600000用于将焦耳转换为kWh，`k_E`为显式能源压力倍率。运输题设模型没有额外计算下降、准备和交接耗电，也没有下降能量回收。不能因此声称真实无人机下降或交接不耗电；中继悬停和通信另有功率模型。

电池有效容量为`C×q`，满足：

$$SOC_{return}=s-E_{sortie}/(Cq)\ \geq\rho$$

默认`ρ=0.2`来自原题，可按当前策略修改。质量和总体积分别不超过机型上限；体积总和可行不等于任意几何形状都能装入货舱。当前没有三维装箱、温度降额或完整电化学模型。

### 7.4 两阶段充电与资源释放

从SOC为s充满的时间，设满充总时长为F：低于90%时为`F×[0.65×(0.9−s)/0.9+0.35]`；90%以上为`F×0.35×(1−s)/0.1`。第一段占满充时长65%，最后10%占35%。

机体占用从准备开始到返航后自身周转结束；电池占用从准备开始到排队充满结束。启用`resource_limits`后，准备工位和充电端口分别是有限容量资源，运输与中继共同竞争。未配置容量时沿用题设并行假设，不能说已经约束实际现场的端口、总供电功率、人员或起降位。低SOC运输初始补能有真实日历安排，深入和联合模型的额外适用限制见下章。

## 8 优化目标与策略版本

### 8.1 共同可行域

各偏好均要求完整需求、箱件唯一、库存可用、质量体积合规、机体与能源兼容、实体不重叠、硬截止、返航储备及当前明确要求的地形、限制区、地面、气象或通信检查。不能靠少送物资、移除硬截止或关闭通信，让某个偏好显得更好。

设T为最后返航时刻，E为能源，L为逐箱优先级加权期望延期：

$$L=\sum_b priority_{d(b)}\max(0,t_{delivery,b}-due_{expected,d(b)})$$

没有期望截止的箱件不产生该项延期；硬截止另作约束。联合方案的T和E包含运输与中继，普通方案为运输口径。`last_delivery_s`表示最后交付，与`makespan_s`最后返航不同。

### 8.2 实际排序

| 规则 | 时间优先的词典序 | 能耗优先的词典序 | 时间能耗折中的词典序 |
|---|---|---|---|
| `deadline_first_v1` | (L,T,E) | (L,E,T) | (L,T+300E,T) |
| `tradeoff_v2` | (T,L,E) | (E,L,T) | (T+300E,L,T) |

词典序表示先比较第一项，再比较同分后的下一项。新界面显式采用v2，旧请求缺少版本时仍按v1，旧Plan原文不重写。系数300是“每kWh折算为300秒”的固定偏好系数，不是人民币、学习结果或公平指标。

三策略可能在有限候选中选中同一计划，也可能只有显示精度相同。前端应说明实际排程是否相同、目标规则和比较范围，不能强制制造不同结果。比较必须核对Snapshot、规则版本和运输/联合范围；不同输入的结果属于情景变化，不能直接归因为偏好或算法优势。

原方案提到的费用优先、基本保障公平和余量优化没有作为完整新目标实现。当前`cost_cny`未配置时为null；“均衡偏好”的准确含义是时间能耗折中。

## 9 快速调度和有限路线池改进

### 9.1 快速多起点构造

入口为`solver.public_api.solve`。先检查输入、范围、模型参数、基地、箱件库存、可用机体、电池、天气和资产，拒绝Mock或已有执行事实被普通静态求解覆盖。正式求解选择每项需求所需的可用实物；多余库存按当前探索的质量/体积评分选择，不直接假定全部出库。

构造过程如下：

1. 按截止、优先级等规则选取当前焦点箱件，尝试有资格的兼容机型。
2. 从单点直送候选开始，尝试同站追加和新站插入；当前快速候选每架次最多访问3个不同需求点，并对其它箱件的插入尝试有数量上限。
3. 每次插入重新计算剩余载荷、路线、升降、能源和时间，枚举真实机体与电池的可行组合。
4. 使用最早可用时间及准备/充电日历安排。检查硬截止、返航储备、释放时刻、固定区间和天气作业窗口。
5. 在候选机型与批次中按构造启发式评分选择，提交后移除已安排箱件，更新机体与电池日历。
6. 使用显式种子和不同构造偏好重复探索，当前最多48轮，有总墙钟预算和停滞停止条件；每个完整候选独立验证，最终按第8章共同目标排序。

构造启发式会使用批次吞吐量、完成时间或能源及小幅随机扰动，不是逐步贪心评分本身就等于最终目标，也不是学习模型或完整ALNS。预算包含预处理和检查；会预留检查时间，但大输入、JIT与平台开销仍需实测，不能承诺每个输入固定秒数。

### 9.2 有限路线池CP-SAT

`mode=improve`可继承同一快照、同一目标和规则的已验证基线，再在剩余预算使用`solver/cp_pool.py`。候选池最多850条，来源包括基线批次、兼容机型替换、拆分、按站点组箱和单箱候选等，不覆盖所有访问序列。

以候选架次选择、真实机体/电池分配和开始时刻为核心，约束需求数量精确覆盖、实物最多使用一次、资源可选区间不重叠、最早可用、截止、能源与地面容量。CP-SAT使用10ms保守时间网格，输出再以原始浮点物理重算。只接受独立检查通过且共同目标严格改善的候选；候选不佳或可选优化器错误时保留有效基线。

用R表示候选池，二元变量xᵣ表示选用候选，aᵦᵣ表示其中是否装有实物箱b。每箱满足“所选候选中的出现次数≤1”，每条需求则按其箱件覆盖系数精确等于required_quantity；没有多余库存选择的实例等价于每个所需箱恰好一次。每个选中架次选择一组兼容机体/电池并具有开始时刻，分别在机体和电池上建立可选占用区间。交接完成偏移加开始时刻不晚于相应硬截止，返航SOC由物理预算约束。工位/端口使用Cumulative容量约束。上述是当前有限模型的变量与约束概括，不代表直接对无限连续航路建立了完整精确模型。

运输深入模型不对非满初始SOC进行完整深层重排；适用性不满足时保留快速有效结果。通信开启后进入另一套有限联合分解，不把850条运输池说成完整通信联合优化。内部有限模型的OPTIMAL不代表全路线空间最优，对外发布仍明确为可行方案。

### 9.3 独立检查与结果语义

`solver/validation.py`从Snapshot重建箱件覆盖、载荷、访问顺序、路线、时间、能源、SOC、机体、电池、充电、地面容量、时限及所要求的通信/天气等。它复用权威物理函数以保持模型口径，但不信任优化器自己填的passed和汇总数字；不是使用一套独立实测物理模型。

| 结果 | 正确解释 |
|---|---|
| FEASIBLE且validation passed | 当前声明范围内找到可发布方案 |
| UNKNOWN | 当前预算、候选或输入条件下未得到已验证方案，不等于物理无解 |
| INFEASIBLE | 有明确模型依据的不可行，需保留证据范围 |
| ERROR / validation_failed | 计算或重建失败，候选不得发布 |
| Job canceled | 独立进程已停止；当前取消Job不发布可确认的中间计划，原有Plan保留 |

`first_feasible_s`是首个独立检查通过候选的耗时。进度只报告阶段、时间与候选数，不能用动画百分比冒充求解完成度。

## 10 运输与通信联合调度

### 10.1 通信问题

通信指运输控制/遥测保障，而非给居民提供公共网络。运输机在需要的全过程中，应能直连固定网关，或经一个中继形成“运输机接入中继＋中继回传网关”同时有效的两跳链路。中继之间不继续转发。当前未建模最大接入人数、带宽竞争、频谱干扰、菲涅耳区和实测传播校准，不虚构并发容量。

默认参数源自原题：2400MHz、系统损耗3dB、遮挡附加损耗10dB、灵敏度−98dBm、裕量8dB、网关离地20m。根据双向收发预算形成直连、接入与回传门限。默认值可在当前输入配置，不是所有设备的通用标准。

### 10.2 连续时间检查

`projected_dem_radio_v1`使用基地所在UTM带和冻结DEM闭四边形像元，限制地理范围、像元尺度与投影畸变。WGS84运动按最长250m分段转为投影直线弦，保留爬升、巡航、下降和交接。

可用区间通过距离阈值交点、扫掠视线三角形与地形像元/高度半空间裁剪求出，同时检查阶段边界、孤立接触和微小数值外扩。直连失效时，所选中继在同一时刻须已建链、仍服务、接入与回传均有效。它是在声明的有限几何传播模型中进行连续时间检查，不是对真实无线电环境的无限精度认证。

### 10.3 联合排程和能源

中继架次包含准备、飞行、建链、驻留、返航、机体周转、能源组件充电。默认2架中继、6套3.2kWh能源组件；服务能耗包含建链和服务期间的悬停/通信，不因某段没有运输机连接就自动忽略空档，也不按连接机数量重复相乘。机体和组件独立预约；有限地面容量开启时与运输共同竞争工位/端口。

求解先产生私有运输松弛的组批、访问顺序与机型，再在有限运输模式及最多48个悬停候选上联合选择开始时刻、机体、电池、中继和服务窗口。几何覆盖需求按候选集合分解为连续原子，随后CP-SAT排程。私有松弛不发布为联合可行方案，最后仍完整独立重建物理和链路。

原题匹配时可以尝试归档23组箱件/访问顺序与3个驻点候选。该模式文件不包含历史起飞时刻、能源、SOC或验算标志；所有数据均从当前输入重算。它提高特定基准的候选可用性，不表示一般输入都能用同一模板解决。当前联合排程限基地可用、初始满SOC资源，不能偷偷将低SOC重置为满电。

### 10.4 展示口径

`metrics`保留运输口径，`joint_metrics`给出中继能源、联合能源、联合最后返航和中继架次数。地图、表格、甘特和Excel读取真实驻点与服务期。空间覆盖页另外在用户选择的AGL和中继站位上计算9至31边长网格，区分直连、中继、不通和未知；这是离散空间采样，不代替实际航迹全过程的连续窗口检查。

## 11 动态事件与保留执行承诺的修复

### 11.1 两条不同的入口

| 入口 | 使用前提 | 事件和计算 | 当前边界 |
|---|---|---|---|
| 零时刻Event＋replan | 整个场景尚未执行 | 机体退出、运输电池退出、中继能源退出、已有点位需求与实物插单 | 应用后版本核对；运输局部/全量，通信全量联合重算 |
| ExecutionEvent＋repair_remaining | 已有独立业务模拟实例 | 机体/电池未来不可用、需求与实物插入、落点不可用、人工天气变化 | 先冻结事实；运输模式中的受支持变化可修复，影响已承诺安全时需人工；联合通信在途修复未具备 |

不能把已在飞的状态塞进普通`solve()`后从头规划。能力报告中的`execution_state=false`描述普通静态入口不接任意执行事实，不表示系统没有独立Execution服务和受控残余修复。

### 11.2 资源依赖与局部范围

图节点用`(plan_id,sortie_id)`精确标识，边表示同一机体或运输电池的时序后继。先求事件直接命中，再沿后继求闭包，区分直接影响、传播影响和已承诺节点。当前图没有把所有通信窗口、空间冲突或地面工位都建成完整依赖边；有限地面资源采用保守共同释放边界。

初始满SOC等条件满足时，先尝试保留未受影响未来架次的资源与时刻，再扩大受影响范围；失败或不适用时在剩余预算全量回退。新增需求直接完整处理新增任务，不能只修旧批次。结果明确报告实际`dependency_local`或`full_recompute`，不声称局部一定更快、改动全局最少或所有目标都改善。

### 11.3 在途承诺与残余输入

当前`execution_commitment_v1`采用保守但可核对的边界：以持久`loaded`或`relay_started`事实确认已开始，而非仅按计划时刻猜测。已经开始准备/装载/飞行/交接的完整架次及其补能尾部作为不可撤销承诺保留。已交付箱件永久保留，在飞机体的机上货物、电池、路线、位置和阶段时序不重置。

服务端从原Plan/Snapshot原文、事实游标、事件序列和当前排程来源冻结Reference。剩余快照扣除已交付与已承诺箱件，重算剩余需求；机体与电池最早可用时间继承承诺尾部，电池预测满充释放与当前观测SOC分开。有限地面条件下保守等待承诺补能尾部，避免旧新重复占用。

新Plan只覆盖残余任务。组合视图保留原承诺来源与新未来来源，额外检查箱件唯一、资源互斥、冻结原文hash、执行revision和事实游标。候选生成不自动采纳；计算后若事实或事件变化，旧候选失效，不能覆盖新状态。

### 11.4 采纳流程

暂停→记录事件→冻结影响和Reference→真实求解残余任务→独立检查→新旧逐箱差异→操作员采纳→模拟设备上传/回执/读回→未来排程生效。失败或未确定不能显示全部应用成功，旧承诺仍受保护。真实飞机在途中临时转向、卸载换机、失效迫降和联合中继窗口重排未在此模型内完成。

误报更正采用追加resolution，不删除原事件；已采纳或正在应用的变更有约束。当前尚有未处理事件时，继续演练和手动推进也不能绕过。

## 12 资源诊断 反事实试算和演练评测

### 12.1 单点诊断和必要下界

单点诊断以额定满SOC与100%SOH、单站往返模型计算安全载重。空载往返不满足能源时明确不可行；中间质量用单调二分取可行下界。相同站点、物资、质量和体积的箱件压缩为计数类，完整枚举有限计数向量与机型，再动态规划依次最小化架次、总能源和累计作业时长。每站最多512个状态，超限或超预算明确limited/partial。

该报告不是可确认Plan，不分配真实机体/电池，不承担并发、充电、需求时限和通信排程。原题当前单点模型得到18批、约59.131296kWh；累计作业时长不能当作并行机队最后返航。另有基于质量/体积等容量的运输架次必要下界，包含精确比值与见证，但不是最少机体、电池数或完整调度最优性证明。

### 12.2 占用与反事实

资源分析读取原Snapshot，给出交付、期望延期、硬截止余量、机体/电池/中继能源区间、充电与并发峰值。占用率须使用报告声明的时间分母，缺省无限端口下的峰值是并发需求，不等于现实必须购买数量。

反事实创建独立Scenario和来源记录，支持增机、增电池、能源/飞行时间倍率、SOH、返航储备，以及已配置有限保障的工位/端口增配，然后真实创建快照求解。保留原需求和硬截止；同输入偏好比较与不同输入试算分开。三档压力只是确定性参数扰动，不是统计概率或概率鲁棒保证。

### 12.3 冻结分区

Q4分析冻结同版联合Plan的运输任务、时刻、中继服务和实际通信来源，通过并查集合并必须同组的连通单元，再枚举2/3个非空组。最多10个连通单元，并限同质、满SOC、零时刻资源。各组资源峰值经区间着色构造实体分配并独立核对。

“共享损失”是各组专属峰值总和减全局共享峰值；“缺口”是专属总配置超出现有库存的部分。最少数量只针对冻结区间与同质资源条件，不能宣称重新组批和排程后的全局最少配置。新增实体建议不会自动变成已有实物。

### 12.4 评测

演练评测为策略对照、quick/improve搜索对照和同一执行残余Reference的修复方法对照。后台协调器串行派发真实Worker，记录快照、种子、预算、版本、源码身份和原始工件。失败、UNKNOWN、取消和超时保留，汇总注明分母，不删除失败样本美化均值。

修复对照使用相同剩余物理输入、释放下界、承诺、目标与预算，比较dependency与full，并报告实际回退路径。策略对照不能直接作为算法创新贡献，少数案例也不能给出通用提升百分比。当前没有完成学习模型、完整鲁棒情景、跨地图统计和所有消融。

## 13 业务仿真 设备接口和状态流

### 13.1 服务器仿真

Execution状态为`ready/running/paused/completed`。服务器基于wall-clock anchor与倍速推进模拟时刻，持久写入装载、交付、中继阶段和资源释放等事实，浏览器关闭不靠前端动画继续记账。暂停或待开始查询不凭计划时间生成新loaded事实；刷新和重启读取持久记录。重置通过新建实例，不删除旧事实。

模拟遥测按已验证实际阶段生成位置；V3增加模型水平速度、垂直速度、阶段结束、载荷和`estimated_soc`。旧`soc`保持计算端点语义，估计字段按声明阶段功率解释，不当作传感器读数。断流保留最后观测并标陈旧，前端不继续外推假实况。

机队看板区分载货运输、交接、空载返航、准备、待命和未来不可用；显示当前目的地、箱件、下一架次、电池与来源。总运输量综合初始、已交付、已承诺和新未来计划，不能仅用扣除在途后的剩余快照统计。例如演练中原32箱加1箱后总数是33，而不是只显示残余待调度量。

### 13.2 DeviceAdapter

抽象接口包括能力查询`capabilities`、遥测流`telemetry_stream`、任务编译`compile_mission`、编译检查`validate_compiled_mission`、上传`upload_mission`、独立读回`read_mission_state`和指令`execute_command`。当前唯一安装的是`SimulationAdapter`，支持未来模拟排程上传、启用和状态查询，不支持在飞完整架次替换，也不连接真机。

HTTP受理、设备ACK和动作完成是三个不同状态。服务器持久存模拟设备独立状态，完成需读回核对Plan及编译内容hash。指令具有执行归属、设备能力、幂等键、版本、有效期和状态机；拒绝、ACK超时、完成回执丢失均保留不同结果。动作可能已发生但完成未确定时，不自动重复有副作用动作，而另行查询状态。

### 13.3 SSE与档案

执行流支持事实cursor和`Last-Event-ID`续传，事实游标与遥测会话序号分开。超前游标返回冲突并要求重读快照。只读档案包含Execution投影、所需Plan/Snapshot原文、事件、变更与指令，校验引用和hash；导入不会创建可控制执行实例，也不会增加交付。

没有本地DEM时，档案仍能查看保存的几何和事实，但不能标为已重新物理认证。没有连续历史遥测的档案不能补造历史实况轨迹。

### 15.3 Job生命周期

Job为queued、running、completed、failed或canceled，与Solver的可行性结果分开。JobManager当前单个Worker并发，多个任务排队；Worker读取冻结input.json，调用纯Solver，写进度与结果。CPU搜索不在HTTP请求线程内长时间执行。

取消会终止并等待真正的子进程退出后记录canceled；服务重启遇到未正常结束Job会标记失败并保留输入，不声称原进程仍在继续。修复派发先持久接纳与幂等回执，再派发并绑定Job，避免相同请求在并发间隙重复计算；未确定派发不盲目重发。

### 15.5 算法对接合同

```python
solve(snapshot, options, progress_callback=None, *, initial_plan=None) -> dict
replan(snapshot, previous_plan, event, options, progress_callback=None) -> dict
repair_remaining(snapshot, reference, options, progress_callback=None) -> dict
validate(snapshot, plan) -> dict
capabilities() -> dict
```

Snapshot和Options是JSON兼容对象，调用不修改输入。后端分配Plan/Snapshot身份；核心Options包含目标、规则、mode、预算、seed、请求范围、父Plan/Event和禁止部分保障等。HTTP的`initial_plan_id/repair_reference_id`是后端加载元数据，不能直接作为未知字段塞给SolverOptions。自定义DEM通过只读`terrain_store`上下文提供，不将本机私有绝对路径写进契约。

JSON Schema为领域数据源，生成Pydantic；操作DTO导出操作Schema与实际OpenAPI，再生成前端HTTP类型。`openapi.draft.json`是历史目标草案，不能覆盖实际快照。Schema文件历史描述中的“G0草案”不表示没有实现，但正式批准状态仍未冻结。

## 18 可用于申报材料的项目与创新表述

### 18.1 项目简介素材

援航面向道路受阻条件下的应急物资运输，将需求、逐箱库存、异构无人机、独立电池、地形与通信资源组织为统一的可追溯调度输入。系统通过限时构造、有限候选优化和独立约束重建，输出具体到架次、箱件、设备和时刻的运输及中继安排；通过地图、地形剖面、资源时间轴和独立任务表帮助调度人员核对方案。任务执行采用服务器业务仿真，条件变化时冻结已发生事实和已开始架次，再对剩余任务计算、比较并采纳调整，最后保留完整复盘与导出记录。

### 18.3 算法技术路线素材

系统首先将业务输入固化为带内容hash的快照，基于DEM、限制区和载荷相关物理生成可行航段与箱件组合；快速阶段通过多起点插入和实体资源日历形成完整方案，改进阶段在有限路线或中继候选上使用约束规划安排机体、能源与服务窗口。所有发布候选由独立检查器重建载荷、时间、能源、资源及通信等条件。动态变化时，根据冻结事实建立剩余任务输入，通过资源后继传播定位可修复范围，并在局部不足时全量回退，最终经差异确认将新未来安排纳入模拟执行。

```python
load_penalty = 1 + 0.12 * (1 - min(1, load_ratio))
batch_bonus = 1 + 0.025 * min(3, cargo_count)
score = base_score * load_penalty / batch_bonus
```

该包为人工规则初始化rule_initialization，不是LLM进化成果。它真实参与搜索，但不保证每例优于标准引擎。联合模式直接采用其他候选、或深入优化保留原基线时，评分调用可能为0，Plan和界面保留实际调用次数。方案规划支持同一Snapshot、目标和规则下的双引擎比较；资源试算、深入、事件重规划和执行剩余修复的客户端继承原引擎。评测可固定引擎，动态修复评测继承基线，不将引擎改变误归因于资源或方法。

### 25.3 四种方法的实际实现

Greedy是问题适配的多起点贪心，按可行箱件组批、截止和资源条件构造并继续尝试；不是一次排序后立即结束的教材单遍贪心。ACO先在自己的预算内构造首解，再按路线信息素和随机选择搜索；信息素在本次运行内部更新。ALNS从自己的首解出发，按随机、能耗较高和空间相关等策略移除部分路线，再修复、按收益更新算子权重。

三种启发式均结合原题适配的覆盖与资源排程。Q3还使用候选中继服务模板和CP约束排程，因此不能将它们称为完全不含约束规划的纯Greedy、纯ACO或纯ALNS。Q3能耗ACO在预算内触发独立CP首解恢复，保留或逐步放宽自身提出的路线分组约束，得到首解后继续蚁群搜索；这不是导入外部或公共初解，混合机制必须与结果一起披露。

CP-SAT使用有限路线及中继候选建立约束模型，安排逐箱覆盖、机体与电池、地面周转及通信服务时间。Q2使用路线池模型；Q3先独立建立自己的可行模板解，再对自己的当前解进行联合改进。模型采用0.1秒保守资源时间包络，报告中的完成时间和能耗使用独立检查器重建的连续值，不使用取整模型目标替代。Q2节能的272路线有限模型，能源和次级完成时间两阶段均记录OPTIMAL；这不证明任意路线、任意连续飞行方案的原问题全局最优。
