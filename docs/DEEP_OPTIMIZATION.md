# 限时深入优化与实际证据

工作台先给出快速真实方案，再可点击“深入优化30秒”。计算沿用当前不可变Snapshot，继承同目标已验算方案，不再次导入或改变资源。进度显示实际阶段，支持取消和刷新恢复；历史记录保留旧方案和优化来源。

路线池包括原方案的批次、各兼容机型、拆分批次、按站点的三种装箱顺序与单箱候选，最多850条。CP-SAT精确覆盖每条需求数量、箱件最多使用一次，并以可选资源区间约束机体和电池占用、最早可用时刻、硬截止及返航SOC。地形/载荷/能耗仍由同一物理模型生成，并由独立检查器完整重算。

它是有限候选池搜索；池外路线、非满初始SOC的深层重排、充电端口容量和通信尚不在该优化模型内。墙钟限时与软件版本会影响所得候选；种子固定也不承诺不同机器逐位一致。无更优候选或可选优化器出错时保留有效基线。不能将有限模型的最优界称为整个灾害调度问题的最优界。

以下是此电脑一次30秒预算实测（均为时间目标、同一输入快照，所有方案独立检查通过）：

| 输入 | 快速基线全部返航/s | 深入优化全部返航/s | 基线/优化能耗/kWh | 基线/优化优先级加权逐箱期望延期/s |
|---|---:|---:|---:|---:|
| 5点32箱 | 7640.19 | 6210.60 | 23.3102 / 21.8076 | 78321.75 / 0 |
| 原题15点80箱 | 10644.61 | 8091.62 | 74.4591 / 89.9890 | 264736.92 / 28428.34 |

这是共同优先级目标下的结果：先减少期望延期，再缩短完成时间，因此原题能耗会增加。没有把能耗改善或历史论文最优值作为承诺。完整输入、Options、基线hash、Outcome与实际运行时间保存在 `evidence/solver/deep-*.json`；快速基线见 `first-*.json`。

模型API参考 [OR-Tools调度文档](https://developers.google.com/optimization/scheduling/job_shop) 与 [Python CpModel](https://or-tools.github.io/docs/python/classortools_1_1sat_1_1python_1_1cp__model_1_1CpModel.html)。
