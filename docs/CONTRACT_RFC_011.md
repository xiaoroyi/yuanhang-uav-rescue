# RFC-011 运输架次容量下界

状态：implementation-branch，用户授权实施，待A/B正式复核。不改变Scenario、Snapshot或Plan。PlanAnalysis增加可选capacity_bound，完整服务输入的只读必要条件诊断，实际OpenAPI与TS同分支更新。

对每项需求，在基地available库存中分别选择需求数量个最轻箱件、最小体积箱件，得到独立质量和体积下界，两套见证不必相同。资源机型仅取基地available运输机与同地available/初始charging且有正可用容量电池的交集。机型额定上限分别取最大质量Q与最大容积V，两个最大值可来自不同机型，此放松只会让下界更弱。

任何完整服务运输方案至少需要max(ceil(M/Q),ceil(L/V))个运输架次。实际实现使用下述保守数值边界代替Q/V，完整有理数比值和每项需求箱件见证一起导出。它忽略路径、能耗、时限、充电、并发、通信和整箱组合，不能称最少机体/电池数量，达到这个下界也不证明完整调度最优。

数值口径：独立容量检查保留原1e-8kg/L容差，质量/体积改用math.fsum从原箱件重建。下界以同一binary64输入的精确Fraction求和，除数取“额定容量+原容差”后向正无穷扩展4个浮点相邻值，覆盖fsum末位/双重舍入保护，再精确向上取整。不用浮点ceil产生整数边界误报。前提为标准binary64、最近舍入环境，未满足或溢出时明确limited。fsum和nextafter的行为依据[Python 3.11官方文档](https://docs.python.org/3.11/library/math.html#math.fsum)。这是一项声明数值模型内的必要下界，不是现实飞行证明。

结果含model_id、status/reason、Snapshot id/hash/version、需求总数、可用机型、额定上限、最小质量/体积、各自下界及合并下界、精确分数与见证ID。Mock、执行事实、基地不可用、库存数量不足或无可用组合时不发布数值下界。当前契约要求非空且正数量需求，零需求等无效输入由原Snapshot校验拒绝，不用0掩盖无效或未评估状态。

前端在资源分析页展示“运输架次容量下界”、当前计划架次和质量/体积口径，可展开查看依据，完整分析JSON保留所有见证。正式Plan的可行性与状态不被这个诊断改变。旧Analysis JSON省略capacity_bound仍可解析；旧字段含义保持。

兼容与验证：仅改容量求和的数值稳定性，不改公式、单位或原容差；必须跑原运输/联合/重规划回归。增加独立小规模装箱枚举、不同最轻/最小体积选择、库存超额、可用资源变化、整数边界与历史Snapshot绑定检查。A-11仍保留部分保障和可证明最小增配等未完成范围。
