5. 系统功能：按用户完整业务链实际实现
5.1 场景与资源输入
实现创建/复制/加载/保存场景、示例导入、JSON/CSV 导入、可下载模板、字段预览与逐行校验，尽可能支持 Excel；需求点、仓库、箱件、救援紧急程度、期望/硬截止时间；无人机型号与实体、电池实体、SOC/SOH、可用时间和位置、兼容关系。物资需求与仓库实有库存必须分开。编辑任一字段应产生新 state_version，不允许只改界面不改后端。
地图上可定位基地、需求点、运输路线；支持场景数据来源/版本、图层切换、坐标与数据校验提示。GeoJSON 限制区、GeoTIFF/DEM、正射图层属于后续深化，但能加载的就真正加载、检查 CRS/覆盖/NoData，数据不合格不得标“净空安全”。
5.2 静态运输计算与不同策略
真实实现 solve(snapshot, options)，至少具备：不可拆箱、唯一分配、质量/容积、可配置机型与实体、可用电池与兼容、返航储备、充电周转、硬截止与可解释的时间/能耗计算。时间优先、能耗优先必须为两次真正针对同一快照的求解，如果没有形成不同解，诚实显示相同。若成本没有费用输入，费用显示未配置，不把能耗伪装成真实人民币。
尽早返回独立验证通过的快速可行初解，允许预算内继续搜索改进；输出机体/电池 ID、箱件 IDs、各站停靠交付、路线 GeoJSON、准备/起飞/返航时间、能耗/SOC、资源释放、指标、状态和约束范围。求解器 UNKNOWN 是未找到或未证明，不是严格无解；严格 INFEASIBLE 仅在模型范围内确证时使用。
5.3 三页指挥工作台（全部按钮必须有行为）
A 场景与资源：导入引导、示例、编辑与保存、检错、单位/字段错误定位、地图定位、设备详情、库存/需求差异、准备创建快照。空/加载/失败/只读/未评估状态齐全。
B 调度主工作台：顶部场景版本、数据来源、计算和验证状态、任务保障、最后交付、最后返航、预计能耗、架次、最低返回 SOC；左侧任务/物资/机队筛选，中部真实地图与路线，右侧策略卡与选中详情，底部可伸缩机体甘特 + 电池甘特/充电。点击需求、航线、架次、箱件、电池，所有视图依同一稳定 ID 联动；地图可缩放、过滤图层、显示停靠与坐标、图例、未评估提示。显示求解阶段、可取消、错误解释和导出。
C 事件复盘与资源诊断：选择未起飞设备退出，提交 Event，新快照重规划，旧/新地图路线高亮对比；显示保留、改派、移除、新增任务以及交付变化。进一步支持电池退出、新需求、落点不可用、禁入区事件（必须先确认事件约束和事实状态），资源增配试算（加机、加电池、充电端口）与独立 what-if 方案比较。能够输出事件记录、差异、方案和任务单。

6. 后端完整业务职责与状态处理（不能仅写增删改查）
至少实现与总纲一致的 /api/v1 端点：/health、/meta/capabilities、场景 import/get/update/validate、snapshots、/solve-jobs create/get/cancel、plan get/compare/confirm/export、事件 create/list、地图资产与 what-if 扩展。以当前仓库正式约定的具体 URL 为准，不另造第二套风格。
- SQLite 保存 scenarios、versions、snapshots、jobs、plans、events、资源预约与必要执行事实；快照和历史方案不可变，文件资产有 hash 与来源。
- 异步提交计算返回 job_id，Worker 在独立进程跑 Solver，保存实际运行时间、日志、seed、预算、停止原因与模型范围；用户编辑场景不会改变旧 Job 输入；进程失败和取消真实可处理。
- 事件有稳定 event_id，按 (scenario_id,event_id) 幂等，版本比较并只应用一次；计划确认在一个数据库事务中校验当前版本、来源、约束检查、资源预约冲突。
- 错误统一 error.code/message/field_path/details/request_id；版本冲突 409，输入错误 422，求解没有解不当成 HTTP 500；缺少外部地图或通信模型返回“未评估/不支持”而不是成功。
- 文件上传控制大小/类型、防路径穿越与恶意文件；密钥不进入 Git；CORS 开发配置明确且不过度开放。
- 真实 JSON/CSV/GeoJSON 导出，以及可重新加载的 Plan/Scenario 历史与运行证据。
7. 前端设计质量：不仅能用，还要非常精致
目标：高端、克制、专业的应急调度 SaaS 工作台，让评委看到有实际产品感的成熟软件，而不是学生作品常见的 Bootstrap 表单堆砌，也不是深色大屏随意铺炫光。
建议默认浅色设计系统：暖白/冷灰页面、白色卡片、石墨深蓝文字、青绿色主要强调、琥珀色事件警告、红色严重冲突。可增加一个精心实现的深色模式，但不应牺牲核心功能。所有颜色具备语义且不单靠颜色区分。使用中文、专业而简洁的真实字段名，保持合理留白、统一 8px spacing scale、适当圆角、精致但克制的阴影、细腻 hover/focus/selected、清晰图例与单位。图标统一 lucide，避免随意 Emoji 作主要 UI 图标。
可采用 shadcn/ui + Radix + TanStack Table + ECharts + MapLibre，以一致的 design tokens 整合，不照搬多个模板形成风格冲突。真实功能的优先级高于动画：骨架加载、空状态、上传状态、校验问题抽屉、可检索表格、数值单位、Tooltip、键盘导航、Toast/确认弹窗、数据来源标识、运行进度、过滤器、可折叠时间轴等都要完善。
地图须有正确点线坐标、适配边界、图层图例、选中高亮、路线与左栏/时间轴双向联动。基础地图瓦片失效时不允许白屏：以可离线的地理网格/坐标背景绘制真正的输入点和计划路线；不要画随机看似正确的卫星照片。通信覆盖与地形净空图层在没有数据时必须标“未评估”。动画以实际计划时间插值，不得自动写回“实际已交付”。
设计和验证视口：至少 1440×900 与 1280×720；可以针对 1920 宽屏优化。窄屏采用抽屉/分页，不要求把整张调度表压成手机一屏。对文字对比度、表格横向滚动、弹窗溢出、地图容器 ResizeObserver、时间轴滚动/缩放仔细检查。不是仅凭“页面能打开”就说高质量：若工具允许，用 Playwright 启动浏览器截图并实际检查版式，发现溢出、重叠、过度留白、底图丢失就调整。
设计展示重点：
1. 首页/场景页能一眼看见输入场景与准备状态。
2. 调度工作台地图是视觉核心，但其空间必须和任务表、指标、时间轴协调。
3. 策略比较呈现有依据的时间/能耗取舍，不摆假的提升百分比。
4. 事件复盘能清楚看出原、新方案的变化，而不是随意让两组曲线换颜色。
5. 所有可见按钮、开关、下载、标签页和菜单要有实际行为；未支持功能禁用并说明，不放可点击但没反应的控件。
8. 双方契约必须按机器可验证原则实现
- Python API：solver/public_api.py 至少提供 solve(snapshot, options, progress_callback=None)、replan(snapshot, previous_plan, event, options, progress_callback=None)、validate(snapshot, plan)、capabilities()，返回已协商的 SolverOutcome。A 不 import backend，C 不重写算法。
- Scenario、Plan、Event、SolveJob 字段必须符合当前 Schema；算法 Plan 与 HTTP Plan 共享 ID/单位/来源。需要扩展字段时先更新协议 RFC、Schema、fixture、Pydantic、OpenAPI/TS、测试并留迁移说明。
- 单位严格统一：坐标 WGS84 [longitude, latitude]，距离/高程 m，质量 kg，体积 L，能耗 kWh，SOC/SOH 0～1，相对时间秒，绝对时间 ISO8601 带时区；不存在或未计算使用 null 而非 0。
- Plan 中 route_geometry 和 sorties[].visits[] 源于算法计算；甘特直接读取算法的 prepare_start_s/takeoff_s/return_s/battery_released_s；前端不重新估算。
- FEASIBLE/OPTIMAL/UNKNOWN/INFEASIBLE/ERROR，validation.passed/failed/partial/not_run，job.queued/running/completed/failed/canceled 是独立维度；has_validated_plan=true 必须有本次真实算法输出的、请求模型范围下完整通过的检查证据。
- 未有费率时 cost_cny=null；强制通信/地形没有模型与数据时返回 UNSUPPORTED_SCOPE 或 INPUT_NOT_READY，不假设通过；历史论文的固定回放不能冒充新输入结果。
- 新旧计划、已完成事实、物资实际状态和事件需保持一致，重规划不能让货箱凭空重新回到基地。
9. 实际测试与交付门槛：每做一块就运行一块
必须真实安装依赖并实际执行命令，修复失败再继续：
1. Schema + fixture 校验，后端数据模型/HTTP/事务测试，前端 TypeScript strict/lint/build、Solver 单元测试；
2. 输入变更（箱重、截止时间、无人机数、电池数）应导致真实重新计算或给出明确可行性变化；
3. 箱件不可重复、资源时段不可重叠、电池和能源储备不违规、硬截止不违规；用故意篡改的方案测试独立检查器真的会拒绝；

5. 故障机退出：事件幂等、新 state_version、旧方案不覆盖、新计划不用故障资源；

必须特别报告在没有原数模完整代码/DEM时，几何与通信的认证无法达到哪一级。算法只在所声明的模型、数据和验证范围内可行，不能宣传真实安全飞行保证。
10. 自动推进顺序和完成定义（不是按天）
你应按依赖自主推进，但每个阶段都要交付能运行的代码，不能先连续制作全部 mock 页面然后最后才想起数据流：
阶段 I：真实审计 + 分支隔离 + 环境安装。 一次执行完成，保存清单；不要重复 G0 大量规划。
阶段 II：真实纵向闭环。 构建一个完整的小规模算法输入→后端快照/Job→真实验证 Plan→地图/架次详情→导出。这是后续所有漂亮 UI 的数据基础。
阶段 III：工程可信度。 双策略、数据库持久化、确认事务、资源甘特、错误/超时/取消、事件重规划与复盘。完整跑通并测试。
阶段 IV：产品设计和精修。 统一组件系统、三页所有主要交互、地图/时间轴联动、响应式、空/失败状态、浏览器截图视觉复核。
阶段 V：深化总纲的 P1/P2。 中继、地形、禁入、资源诊断、情景分析、AI/ODM/SITL 等逐项检查数据及依赖，能真实落地则实现并测试，否则留有诚实的模块边界、所需外部条件和下一步任务，不能伪称完成。
阶段 VI：完整回归与交付。 一键启动、README、演示数据、回归测试、E2E、证据与明日团队交接报告。修复关键缺陷。根据本分支产物建立 PR 或说明如何合并，不自动覆盖主分支。
不要每一阶段做完就因认为“任务较大”停止回答。若上下文/额度/执行时间不足，先保存代码和 docs/IMPLEMENTATION_STATUS.md，真实测试能跑的部分，给出一条精确的续跑命令/提示词。不得声称“全部完成”而没有证据。
